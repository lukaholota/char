# KR14.5 — прогін предметів у production

**Виконує власник.** Агент цей файл написав і перевірив на `spells_test`, у `spells` не писав.

Прогін не має SQL-скрипта: контент їде сідом ([Р17](../DECISIONS.md)), а сід ідемпотентний.
Команда одна, але перед нею є перевірка, яка коштує хвилину й ловить єдину справді
небезпечну ситуацію — розбіжність `magic_item_id` між базою і корпусом.

## Що зміниться

| | До | Після |
|---|---:|---:|
| Рядків `magic_item` | 248 (виміряно 2026-08-21) | **475** |
| З них перекладено партіями O14 | 0 | 268 |
| `pers_magic_item` | скільки є | **стільки ж** |
| `_MagicItemToSpell` | скільки є | **стільки ж** |

227 рядків додасться, 248 оновиться. Сід не видаляє нічого й не перенумеровує: у `update`
він явно викидає `magicItemId`, тому наявні публічні адреси `/magic-items/NNNN` не рухаються.
Нові 227 адрес почнуть відповідати — це і є мета KR14.1 (база = каталог).

## 0. Перед прогоном — знімок і перевірка id

```sql
-- скільки є зараз
SELECT count(*) AS rows, count(short_description) AS with_short FROM magic_item;
SELECT count(*) FROM pers_magic_item;
SELECT count(*) FROM "_MagicItemToSpell";

-- знімок таблиці, щоб було куди відкотитися
CREATE TABLE magic_item_backup_2026_08_22 AS SELECT * FROM magic_item;
```

Далі — єдина перевірка, яку варто зробити руками. Сід шукає рядок за `eng_name` і створює
новий із **явним** `magic_item_id`. Якщо в базі якийсь `eng_name` стоїть під іншим id, ніж
у корпусі, вставка нового рядка вдариться в первинний ключ і транзакція впаде на середині.

```bash
npx tsx scripts/aidedd/check-prod-magic-item-ids.ts --target prod
```

Скрипт нічого не пише: він читає корпус із `prisma/seed/magic-items/baseline.json` плюс партії,
звіряє пари `eng_name` ↔ `magic_item_id` з базою і друкує перелік розбіжностей. Порожній
перелік — можна запускати сід. Непорожній — **не запускати**, принести перелік у чат.

## 2. Перевірка після прогону

```sql
SELECT count(*) FROM magic_item;                    -- 475
SELECT count(*) FROM pers_magic_item;               -- те саме число, що в кроці 0
SELECT count(*) FROM "_MagicItemToSpell";           -- те саме число, що в кроці 0
SELECT count(*) FROM magic_item WHERE description ILIKE '%урон%';   -- 27, і це залишок
SELECT count(*) FROM magic_item WHERE short_description IS NULL
   OR btrim(short_description) = '';                -- 124, теж залишок
SELECT count(*) FROM magic_item WHERE name !~ '\[.+\]$';            -- 1 (Rod of the Pact Keeper +1)
```

Числа «27 / 124 / 1» — це неперекладена черга O14, а не поломка: ті самі числа тримає
`tests/db/magic-items-seeded.test.ts` на `spells_test`.

## 3. Повторний прогін — доказ ідемпотентності

```bash
bun run seed:magic-items:prod
```

Друга спроба має дати той самий вивід і не змінити жодного рядка.

## 4. Каталог

```bash
bun run generate:magic-items
```

Після цього `src/lib/generated/magicItems.json` має містити **475** записів, а не 248 і не 472 —
база й каталог зійдуться вперше. Далі варто підняти поріг гарда в
[scripts/aidedd/existing-magic-items.ts](../../scripts/aidedd/existing-magic-items.ts):
`EXPECTED_CATALOG_SIZE` з 472 на 475. **Робити це тільки після кроку 4** — інакше всі скрипти
aidedd почнуть падати на каталозі, який ще не перезібрано.

## Якщо щось пішло не так

```sql
BEGIN;
DELETE FROM magic_item
 WHERE magic_item_id NOT IN (SELECT magic_item_id FROM magic_item_backup_2026_08_22);
UPDATE magic_item m SET
  name = b.name, item_type = b.item_type, rarity = b.rarity,
  requires_attunement = b.requires_attunement, eng_name = b.eng_name,
  description = b.description, short_description = b.short_description,
  weapon_proficiencies = b.weapon_proficiencies,
  weapon_proficiencies_special = b.weapon_proficiencies_special,
  bonus_to_ac = b.bonus_to_ac, bonus_to_ranged_damage = b.bonus_to_ranged_damage,
  bonus_to_saving_throws = b.bonus_to_saving_throws,
  no_armor_or_shield_for_ac_bonus = b.no_armor_or_shield_for_ac_bonus, ruleset = b.ruleset
FROM magic_item_backup_2026_08_22 b WHERE m.magic_item_id = b.magic_item_id;
SELECT count(*) FROM magic_item;   -- має дати 248
COMMIT;
```

`DELETE` б'є лише по рядках, яких до прогону не було, тож `pers_magic_item` втратити нічого
не може — на нові id ще ніхто не посилається. Цей самий відкат агент прогнав на `spells_test`
десять разів під час доведення тестів червоними, і знімок бази щоразу збігався побайтово.
