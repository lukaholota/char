# KR14.1 — Одне джерело істини для предметів і знешкоджена міна

**Ціль:** [O14](README.md) · **Статус:** ✅ закрито 2026-08-22 (прогін у прод — за власником) · **Залежить від:** рішень власника
[1](README.md#відкриті-питання-потрібне-рішення-власника) (міна) і
[6](README.md#відкриті-питання-потрібне-рішення-власника) (2024-пул)

## Мета

Зробити так, щоб каталог предметів не можна було зруйнувати випадковою збіркою, і щоб перед
початком імпорту існувало **одне** місце, яке відповідає на питання «скільки в нас предметів
і який у них текст». Зараз відповідей три — 248 у базі, 472 у генерованому файлі, 445 у
нормалізованому — і жодна з них не переживає `bun run generate:content`.

## Міна, дослівно

`generate:content` висить на `prebuild` і викликається в обох джобах CI — перед `tsc` і перед
`docker build`. Він запускає `generate-magic-items.ts`, той читає `magic_item` з
`where: { ruleset: RULES_2014 }` і перезаписує `src/lib/generated/magicItems.json`. У базі 248
рядків, у файлі 472. Файл у `.gitignore` **і не відстежується**, тому відкотити зміну з git
неможливо: 224 записи каталогу зникають назавжди, разом із їхніми публічними URL
(`/magic-items/1001`…`/magic-items/1224`) і рядками в `sitemap.ts`.

Пом'якшує це одне: [prisma/seed/magicItemSeed.ts](../../prisma/seed/magicItemSeed.ts)
відстежується і містить **рівно ті самі 472 записи** (перевірено 2026-08-21 множинами назв —
0 розбіжностей в обидві сторони; 248 id < 1000, 224 id ≥ 1000, максимум 1224, дублікатів
`magicItemId` і `engName` немає). Тобто текст не втрачається — втрачається каталог до
наступного прогону сіду.

## Узгоджений scope

1. **Гард у генераторі.** `scripts/generate-magic-items.ts` падає з явним повідомленням, якщо
   з бази прийшло менше за поріг, замість мовчки писати обрізаний файл. Поріг — константа
   в скрипті поруч із поясненням, чому вона там; після сіду її піднімають, а не прибирають.
2. **Рішення по міні застосоване** (питання 1): або `bun run seed:magic-items:prod` прогнано
   власником і база стала 472, або сід свідомо відкладено до кінця O14, і тоді гард — єдине,
   що тримає каталог.
3. **`scripts/build-magic-items-2014.ts` неможливо запустити випадково** — видалити або
   поставити `throw` на старті. Скрипт не відстежується git і **губить поля**: переносить лише
   `bonusToAC`, зануляє `bonusToRangedDamage`, `noArmorOrShieldForACBonus` і `givesSpells`, а
   `bonusToSavingThrows` і `weaponProficienciesSpecial` не переносить ніколи.
4. **Переліки aidedd у git.** `data/aidedd/lists/*.json` зараз не закомічені, хоча коментар
   у `.gitignore` каже, що переліки лишаються — це вхід для рев'ю, і `magic-items-2014.json`
   (473 слаги) знадобиться [KR14.2](kr14.2-fetch-and-parse.md).
5. **Рішення про 2024-пул** (питання 6) записане. Зараз `magicItemsData.ts` синтезує id як
   `20000 + index + 1`, тобто публічна адреса 2024-предмета — це його порядковий номер у файлі.
6. **Джерело істини записане власником у [DECISIONS.md](../DECISIONS.md)** — окремим рішенням,
   а не в цьому файлі.
7. **Виміряти `pers_magic_item`** — скільки рядків і на які `magic_item_id` вони посилаються.
   Перезапис тексту id не рухає, але цифру треба знати до, а не після.

## Готово, коли

- [x] `bun run generate:magic-items` проти бази з 248 рядками **падає** з повідомленням, у
      якому видно очікуване й фактичне число. Доведено реальним прогоном проти робочої бази:
      «база віддала 248, очікували щонайменше 472», код виходу 1, md5 `magicItems.json` до й
      після — той самий, у файлі лишилося 472 записи.
- [x] Рішення по питанню 1 застосоване — обрано **сід**. На клоні `spells_test`, приведеному до
      точного стану прода (248 рядків, дамп `magic_item` + `_MagicItemToSpell`),
      `bun run seed:magic-items:test` дав **473** рядки: 472 базового корпусу плюс
      `Unbreakable Arrow`. З них 11 рідкості `ARTIFACT`. Прогін у прод готовий і чекає власника.
- [x] Партія 01 живе в сідах: `prisma/seed/magic-items/batch-01.json` (29 предметів),

- [x] `scripts/build-magic-items-2014.ts` не запускається — видалений. Файл не був у git, тож

- [x] `data/aidedd/lists/magic-items-2014.json` містить **473** слуги (перевірено, поле `count`).
      Теку не комітили окремо — вона потрапить у git разом із рештою дерева.
- [x] Рішення про джерело істини записане в [DECISIONS.md](../DECISIONS.md) як
      **[Р17](../DECISIONS.md#р17)** — контент їде сідами, `db/changes/` лишається під схему.
      Це ж закрило відкрите питання 5 в [O13](../o13-2024-completeness/README.md).

      предмети каталогу поки що нічиї.
- [x] `bun run test`, `bun run test:integration`, `bunx tsc --noEmit`, `bun run lint` — див.

### Що з цього списку змінилося проти початкової редакції

- Рішення по 2024-пулу (питання 6) **не приймалося** — воно про `magicItemsData.ts` і синтетичні
  id `20000 + index`, тобто про каталог 2024, а цей KR закриває 2014. Лишається відкритим.
- Число стало **473, а не 472**: `Unbreakable Arrow` — справжній предмет, якого в каталозі не
  було. Деталі в журналі.

## Журнал

### 2026-08-21 — KR створено

### 2026-08-22 — KR закрито: партія переїхала в сіди, міна знешкоджена

**Головне рішення власника, яке переписало обсяг.** Партія 01 приїхала файлом
`db/changes/2026-08-22-o14-magic-items-batch-01.sql`. Реакція власника: «а чого не в сідах?
чого скриптом, який потім загубиться?». Тому KR перестав бути про «прогнати сід» і став про
«зробити так, щоб наступні ~15 партій не повторили ту саму помилку». Записано як
[Р17](../DECISIONS.md#р17).

**Сюрприз 1: `spells_test` уже був на 472.** Розрив 248/472 існував лише в **проді** — на клоні
хтось уже ганяв сід. Тобто демонстрація «до і після» на тому клоні нічого б не довела. Довелося
спершу привести `spells_test` до точного стану прода дампом `magic_item` і `_MagicItemToSpell`,
і вже тоді ганяти сід. Урок той самий, що в KR13.1, тільки з іншого боку: **клон не є доказом
стану прода**.

**Сюрприз 2: партія додає предмет, якого в каталозі не було.** `Unbreakable Arrow` (id 1304) —
не переклад наявного запису, а новий предмет. Каталог росте 472 → 473, і це ламає
`tests/content/magic-items-2014.test.ts`, який фіксує рівно 472. Тест **правильно** лишили як є:
`magicItems.json` регенерується з бази, а база стане 473 тільки після прогону власника. До того
моменту 472 — чесне число.

**Сюрприз 3: другий «новий» предмет виявився дублікатом.** SQL створював
`Ammunition +1, +2, or +3` (id 1308) — одну сторінку aidedd, що зліплює три рівні боєприпасів.
У каталозі вони вже живуть **окремими записами** з різною рідкістю: `Ammunition +1` (93,
UNCOMMON), `+2` (94, RARE), `+3` (95, VERY_RARE). Злитий четвертий запис показав би в каталозі
дубль без вибору рівня. Тому 1308 **не створюється**, а слуг `ammunition-1-2-or-3` позначено
покритим у `COVERED_BY_EXISTING_ENTRIES`, щоб його не рахували за дірку в покритті. Перевірено:
на 93/94/95 не посилається жоден персонаж.

**Сюрприз 4: два артефакти перекладу розійшлися в тексті.** *(розв'язано в партії 02 —
перезапуск імпортера показав, що корпус розійшовся зі своїм власним входом; правий бік —
партія перекладу, «самоцвіту». Деталі в [журналі KR14.4](kr14.4-translation-batches.md#журнал).)*

**Сюрприз 4: два артефакти перекладу розійшлися в тексті.**
`data/aidedd/translations/magic-items-2014/batch-01.json` і `data/aidedd/magic-items-2014.json`
дають різний текст для `Elemental Gem`: «магія самоцвіт**у**» проти «магія самоцвіт**а**»
(і те саме в наступному реченні). SQL зібрано з другого. Щоб переїзд SQL → сід не протягнув
мовчазну правку тексту, партію зібрано з **того самого джерела, що й SQL** — тобто текст
перенесено дослівно, з «самоцвіта». Яка форма правильна — окреме питання до перекладу, не до
цього KR. Це і є аргумент за один сід-facing файл замість двох робочих.

**Що зроблено з міною.** `generate-magic-items.ts` отримав `failOnShrunkCatalog` — поріг 472 з
поясненням, чому він там і чому його **піднімають**, а не прибирають. Доведено прогоном проти
робочої бази: скрипт упав, файл не змінився. Тобто `bun run build` тепер не може тихо викинути
225 предметів — він падає до запису.

**SQL знешкоджено інакше, ніж просто видаленням.** Файл лишився на місці, але його вміст —
`RAISE EXCEPTION` з поясненням, куди переїхала партія. Причина: початкова версія розійшлася по
чатах, і видалений файл від повторного застосування не рятує. Перевірено: `psql -f` на ньому
падає.

**Індекси R14.** `pers_user_id_idx`, `pers_folder_id_idx`, `pers_parentpersid_idx` у робочій
базі **є**. `bun run db:pull` дав **нульовий діф** і в `prisma/schema.prisma`, і в
`db/schema.sql` — власник уже пулив після застосування. Індекси присутні в обох артефактах
(`@@index([userId])` у моделі `Pers`, три `CREATE INDEX` у дампі). Нульовий діф тут — правильний
результат, а не пропущена робота.

**Що НЕ зроблено свідомо.** `bun run seed:magic-items:prod` не ганявся — це прогін у робочу базу,
його робить власник. Доки він не зроблений, у проді лишається 248 рядків, і кожен `bun run build`
падатиме на гарді. Це навмисно: падіння дешевше за втрату каталогу.
