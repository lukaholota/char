# Посібник автора готових білдів (KR49.8)

Для агента, який уперше пише готовий пресет 2014 за авторським прикладом RPGbot. Посібник
самодостатній: після нього один пресет має коштувати ~30–40 тис. токенів. Зразки: специфікації в
`data/rpgbot/build-specs/` (`monk-human-open-hand-2014.json`, `paladin-oath-of-vengeance-2014.json`
— повні; `rogue-mastermind-2014.json` — Таші; `paladin-oath-of-redemption-2014.json` — blocked).

## Що ви робите

Ви пишете **одну специфікацію** `data/rpgbot/build-specs/<slug>.json`. Компілятор сам створює
`data/rpgbot/builds/build-<slug>.json` (рецепт: вузли й план рівнів — це текст статті, а не ваш),
`data/rpgbot/ready-builds/<slug>.json` (пресет) і оновлює `builds.json`. Рецепти й пресети руками
не редагуйте: наступна компіляція їх перезапише. Не чіпайте `builds.json`, `build-ledger-*`,
статті (`uk/`, `authoring/`), `src/lib/optimization/ready-preset*.ts`, не комітьте й не пушіть.
Облік (ledger) регенерує інтегратор раз наприкінці.

Якщо приклад автора не виконується чинною платформою — **не вимучуйте**: запишіть blocked-специфікацію
з точною причиною (розділ «Неповнота» нижче). Це теж результат.

## Команди (усі з кореня репозиторію, bun)

| Команда | Що робить |
|---|---|
| `bun scripts/rpgbot/show-build-source.ts <articleSlug> <exampleSection>` | Друкує розділ-приклад, таблицю характеристик (базові значення) і рядок 1-го рівня; перші рядки містять `reviewedRevision` |
| `bun scripts/rpgbot/show-catalog.ts search <текст>` | Знаходить ключі класів, підкласів, рас, підрас, передісторій, рис, зброї |
| `bun scripts/rpgbot/show-catalog.ts class\|race\|background\|feat <KEY>` | Клас: групи спорядження та класові вибори; раса: підвищення, підраси, мови; передісторія: навички; риса: опції |
| `bun scripts/rpgbot/show-catalog.ts levels <CLASS>` / `subclass <CLASS>/<SUBCLASS>` | Для прогресії: на яких рівнях класу підклас, підвищення/риса, експертиза, вибори (`classOptions`/`subclassOptions`), приріст заклинань, здібності за рівнями |
| `bun scripts/rpgbot/compile-build.ts <slug> --dry-run` | Компіляція + перевірки, нічого не пише |
| `bun scripts/rpgbot/compile-build.ts <slug>` | Те саме й запис трьох файлів — лише якщо немає жодної помилки |
| `bun scripts/rpgbot/compile-build.ts --all --verify` | Чи збігаються файли на диску з компіляцією специфікацій |
| `bun scripts/rpgbot/check-build.ts <slug>` (`--all`, `--db`) | Незалежна перевірка збереженого пресета й підсумок «що буде створено», а для рецепта з прогресією — «що буде на рівні N» (підклас, підвищення, вибори, заклинання, здібності); `--db` читає каталог із локальної `spells_test:5433` |

Звідки каталог: за замовчуванням `src/lib/generated/creator-content-2014.json` (його ж читає сторінка
пресета); паритет із базою доводить `tests/content/creator-content-parity.test.ts`.

## Покроково

### 1. Виберіть кандидата

Кандидат — розділ «Example Build» у `data/rpgbot/build-ledger-2014.json` (`buildCandidates`, поле
`disposition: "incomplete-unstructured"`). Перед початком переконайтеся, що жоден інший агент не взяв
той самий розділ: `ls data/rpgbot/build-specs data/rpgbot/ready-builds` і перегляньте
`articleSlug` + `exampleSection` у чужих рецептах (`rg '"sectionId": "<exampleSection>"' data/rpgbot/builds`).

Швидка відсіювальна перевірка (5 хвилин, до написання чогось):
1. **Клас без вибору заклинань на 1-му рівні** (Варвар, Воїн, Монах, Пройдисвіт, Паладин, Слідопит). Заклинателів
   і клас із підкласом на 1-му рівні веде інший агент.
2. **Підвищення раси**: `show-catalog.ts race <KEY>`. Якщо там «УВАГА: лише підвищення за правилами Таші»
   (раси «Монстрів Мультивсесвіту», Spelljammer, Своя раса) або автор «змінює походження» — задайте
   `racialAbilityRules: "tasha"` (розділ «Правила Таші» нижче). Це більше не blocked.
3. Автор не змінює таблицю підвищень «власним походженням» (+2 в іншу характеристику, ніж у раси), не купує
   спорядження за стартове золото як обовʼязковий крок, не стартує з іншого класу (мультиклас) і не
   використовує передісторію, якої нема в каталозі (`show-catalog.ts search`).
4. Передісторія, раса, підраса, риса, підклас є в каталозі (`show-catalog.ts`).

### 2. Прочитайте приклад

`bun scripts/rpgbot/show-build-source.ts <articleSlug> <exampleSection>` (довший текст: `SECTION_LIMIT=2000`).
Звідси беріть **тільки те, що автор називає**: расу/підрасу/варіант, характеристики (базові), навички, передісторію,
мови, спорядження 1-го рівня, класові вибори, риси. Скопіюйте `reviewedRevision` у специфікацію.

Приклад-фрагмент для рядка 1-го рівня таблиці бере спорядження: «візьміть спис, будь-який набір і 10 дротиків».
Усе, чого автор не називає (набір, мова, навичка, на яку він лише натякає), — **вибір платформи** (див. нижче).

### 3. Напишіть специфікацію

`data/rpgbot/build-specs/<slug>.json`, `<slug>` = імʼя файлу пресета (`<клас>-<підклас>-2014`), `buildId` стане `build-<slug>`.
Образець (`monk-human-open-hand-2014.json`, скорочено):

```json
{
  "status": "ready", "ruleset": "RULES_2014",
  "articleSlug": "monk-2014",
  "reviewedRevision": { "translationRevisionId": "translation-rpgbot-monk-2014-draft1", "sourceRevisionId": "rpgbot-d0ca…" },
  "exampleSection": "section-example", "levelTableSection": "section-levels",
  "classKey": "MONK_2014", "subclassKey": "WAY_OF_THE_OPEN_HAND",
  "raceKey": "HUMAN_2014", "backgroundKey": "CRIMINAL",
  "abilityScores": { "STR": 8, "DEX": 15, "CON": 15, "INT": 8, "WIS": 15, "CHA": 8 },
  "preset": {
    "title": "…", "description": "…", "subraceKey": null, "racialAbilities": [],
    "skills": { "selectedClass": ["INSIGHT", "STEALTH"], "race": [], "background": ["PERCEPTION"] },
    "expertise": [], "classOptions": [], "languages": ["ELVISH"],
    "equipment": [ { "group": 1, "option": "b", "weapons": ["SPEAR"] }, { "group": 2, "option": "b", "weapons": [] }, { "group": 3, "option": "a", "weapons": [] } ],
    "featOptionName": null, "skillSection": "section-skills-and-tools", "featSection": null, "equipmentSection": "section-levels",
    "abilityExplanation": "…", "skillExplanation": "…", "equipmentExplanation": "…"
  }
}
```

Поля поза `preset`:
- `variantKey` (напр. `HUMAN_VARIANT`) і `featKey` — лише якщо вони є; підклас лишається **майбутнім** (рівень 1 його не записує).
- `abilityScores` — базові значення купівлі очок (8–15, сума вартості 27); компілятор попередить, якщо вони не збігаються з таблицею автора.
- `levelPlans`: `{ "levels": "all" | [1,2,3], "notes": false, "featuresColumn": 1, "notesColumn": 2 }`. Типові колонки таблиці рівнів:
  `Рівень | Риси та уміння | Примітки` (1, 2). Якщо є додаткова колонка (Люті, Підступна атака) — `featuresColumn: 2` або `1`
  залежно від положення «Риси та уміння», `notesColumn` — останній. `show-build-source.ts` показує рядок 1-го рівня: перевірте, що це саме уміння.
- `nodeSections` — зазвичай не потрібно (за замовчуванням усі вкладені розділи прикладу, крім таблиці рівнів).
- `incomplete`: `[{ "field": "…", "reason": "…", "section": "<sectionId>" }]` — те, що автор радить, але пресет не відтворює.
- Розділи в `preset`: `skillSection` і `featSection` **мають бути серед вузлів** (вкладені розділи прикладу); `featSection: null`, якщо риси немає;
  `equipmentSection` — зазвичай таблиця рівнів.

Значення `preset.*`:
- **`racialAbilities`** — вибір гнучких підвищень раси (basic). Людина — `[]`, Варіант людини — дві характеристики, Напівельф — дві.
  Разом із `"racialAbilityRules": "tasha"` — вибір за правилами Таші (розділ нижче).
- **`skills`**: `selectedClass` — навички від класу, `race` — від раси (Варіант людини 1, Напівельф 2), `background` — **заміни** для
  навичок передісторії, що повторюють уже наявні. Якщо повторів нема — `[]`; якщо повтор один — рівно одна заміна. Фіксовані навички раси й передісторії
  не вказуються (додаються самі).
- **`expertise`** — навички з уже наявних (клас дає кількість: Пройдисвіт 2).
- **`classOptions`** — англійські назви класових виборів 1-го рівня (`Dueling`, `Favored Enemy`). По одному на групу.
- **`languages`** — рівно стільки, скільки персонаж обирає (раса + передісторія + клас), без уже відомих.
- **`equipment`** — **усі** групи класу, по одному вибору: `group`, `option` (літера), `weapons` — назви `SPEAR`, `HALBERD` лише для варіантів «на вибір»
  (`show-catalog.ts class <KEY>` показує групи, літери й кількість зброї).
- **`featOptionName`** — англійська назва опції риси; `null`, якщо у риси немає опцій у каталозі.
- **Пояснення** — коротка українська: що автор радить і що платформа підставила за вас.

Українська: апостроф лише `ʼ` (U+02BC), без `'`. Власні назви беріть із тексту статті (маркери `{{English}}` та словник),
нових термінів не вигадуйте; сумніви — скіл `dnd-ua-translation`.

### 4. Скомпілюйте

```
bun scripts/rpgbot/compile-build.ts <slug> --dry-run     # читаєте помилки, виправляєте специфікацію
bun scripts/rpgbot/compile-build.ts <slug>               # запис
bun scripts/rpgbot/check-build.ts <slug>                 # огляд: підсумок «що буде створено»
```

Компілятор не пише нічого, поки є хоч одна помилка (інакше невалідний пресет зламав би галерею для всіх).

### 5. Звірте підсумок

`check-build.ts` друкує остаточні характеристики, навички, експертизу, мови й **назви** вибраного спорядження. Порівняйте з авторським текстом:
літера варіанта спорядження не гарантує, що це «Набір священика», а не «Набір мандрівника» — читайте назви, і пояснення мусить відповідати.
Попередження «Імовірні вибори платформи без позначки» означає, що в `*Explanation` немає слів «за вас» / «вибір платформи».

### 6. Тести

```
DATABASE_URL=postgresql://none:none@127.0.0.1:1/none_test bunx vitest run \
  src/lib/optimization/ready-presets-all.test.ts src/lib/optimization/ready-preset-catalog.test.ts
./scripts/local-test-db.sh status && bun run test:integration \
  tests/actions/rpgbot-ready-presets-all.shard-1.test.ts … shard-4.test.ts
```

`ready-presets-all.test.ts` (без БД) перевіряє кожен пресет і що файли відповідають специфікаціям. Шарди (БД, копії воркерів) створюють кожен пресет справжнім
`createCharacter` і звіряють персонажа з чернеткою: клас/раса/підраса/передісторія/риса, характеристики (ті самі функції, що й у створенні), навички й експертизу,
мови, склад зброї та броні з вибраних груп, класові/расові вибори, слоти заклинань, заклинання, HP>0 і `currentHp=maxHp`. Окремий список slug вести не треба:
тести обходять `data/rpgbot/ready-builds/*.json`.

Після додавання, видалення чи перейменування пресета перегенеруйте глобальний пошук: `bun run generate:rpgbot-search`
(це `bun scripts/rpgbot/generate-search.ts --apply`; без `--apply` лише перегляд). Він оновлює
`src/lib/generated/optimization-preset-search-2014.json` (назва, клас, підклас і їхні англійські назви; у пошуку
такий пункт веде на `/char/create?preset=<slug>`). Тест `tests/content/rpgbot-omni-search.test.ts` падає, якщо файл застарів.

## Інваріанти й типові помилки

| Повідомлення | Причина → виправлення |
|---|---|
| `Невідомий розділ «x» (поле)` | Помилка id розділу → виберіть із переліку «Розділи прикладу» у повідомленні |
| `Немає в каталозі 2014: раса «HALF_ORC»` | Ключ без суфікса → використайте «Схожі: …» або `show-catalog.ts search` |
| `Стаття оновилась після огляду` | Стаття змінилась → перечитайте `show-build-source.ts`, оновіть `reviewedRevision` |
| `Передісторія дублює N навичок … потрібно рівно N замін` | Повтор навички → `skills.background` = N навичок, яких ще нема (автор часто називає заміну; інакше `PERCEPTION` і позначте) |
| `Передісторія нічого не дублює, … має бути порожнім` | Не додавайте заміни без повтору |
| `skills.selectedClass: X недоступна` | Навичка не з класового списку або вже дана расою |
| `Експертиза не з навичок персонажа` | Експертиза лише з навичок, що вже є (разом із фіксованими) |
| `Група спорядження 2 не має варіанта c` | Літери варіантів із `show-catalog.ts class` |
| `потребує 2 видів зброї` / `Зброя X недоступна` | Для варіанта «на вибір» вкажіть рівно стільки зброї, скільки показано; назви `WEAPON_NAME` |
| `Бракує вибору «Fighting Style» у classOptions` | Клас вимагає по одному вибору на групу |
| `Мови: персонаж обирає N, а в пресеті M` | Рахуйте мови раси + передісторії + класу; відомі мови не повторюйте |
| `racialAbilities … дає вибір 2 підвищень` | Варіант людини, Напівельф: дві різні характеристики |
| `featOptionName … не належить риси` | Для риси з опціями вкажіть її англійську назву; для риси без опцій — `null` |
| `не входить у вузли рецепта` | `skillSection`/`featSection` мають бути вкладеними розділами прикладу |
| `Порожній текст умінь … featuresColumn` | У таблиці рівнів інший порядок колонок |

Дублі володінь, експертиза, мови, групи спорядження — найчастіші помилки; тест не пропустить лишній вибір, а `check-build` назве точну причину.

## Правила Таші (змінене походження)

Коли раса має в каталозі лише підвищення Таші (MPMM, Spelljammer, «Своя раса») або автор розподіляє підвищення
«за власним походженням», у `preset` додайте `"racialAbilityRules": "tasha"` і `racialAbilities` — **плоский список
характеристик по групах каталогу підряд** (група 1, потім група 2…; підраса додає свої групи в кінець).
Групи й їхня кількість — у `show-catalog.ts race <KEY>`, рядок «групи Таші»:

| Раса | Групи | Автор: +2 до Спритності, +1 до Харизми | Автор: +1/+1/+1 до STR, DEX, CON |
|---|---|---|---|
| MPMM / Spelljammer (напр. `HOBGOBLIN_MPMM`) | 1) +1 до 2 різних, 2) +1 до 1 (повтор між групами дозволено) | `["DEX", "CHA", "DEX"]` | `["STR", "DEX", "CON"]` |
| `CUSTOM_LINEAGE_TCE` | 1) +2 до 1 | `["DEX"]` (+2 до одної) | недоступно в каталозі |
| Класична раса, напр. `ELF_2014` | 1) +2 до 1; підраса додає 2) +1 до 1 (різні) | `["DEX", "WIS"]` | недоступно в каталозі |

Правила, які перевіряє `compile-build`/`check-build`: кількість = сума груп; у межах групи без повторів; якщо
групи раси й підраси всі «різні», повтор між ними теж заборонений. Каталог не дозволяє +1/+1/+1 для класичних рас —
тоді blocked. Підсумок показано в `check-build` («Расові підвищення за правилами Таші: група 1 → DEX, CHA…»);
звіряйте його з таблицею автора. `abilityScores` лишаються базовими значеннями купівлі очок.

```json
"racialAbilities": ["DEX", "CHA", "DEX"], "racialAbilityRules": "tasha"
```

Сервер рахує це тими самими функціями, що створення (`isDefaultASI: false`, `tashaChoices`); класичні расові бонуси
в такому режимі не додаються. Зразок: `data/rpgbot/build-specs/rogue-mastermind-2014.json`.

## Заклинання від рис 2014

Пресет записує заклинання лише таких рис 2014: `MAGIC_INITIATE` (2 замовляння + 1 заклинання 1-го рівня з одного
списку: бард, клірик, друїд, чародій, чорнокнижник, чарівник), `RITUAL_CASTER` (2 ритуальні заклинання 1-го рівня з
одного списку), `ARTIFICER_INITIATE` (замовлення + заклинання 1-го рівня зі списку винахідника), `FEY_TOUCHED`
(Туманний крок + 1 заклинання 1-го рівня Пророкування/Чарів), `SHADOW_TOUCHED` (Невидимість + 1 заклинання
Ілюзії/Некромантії), `TELEKINETIC` (Магічна рука), `TELEPATHIC` (Виявлення думок). Поіменні заклинання сервер дає сам;
обрані ви називаєте у `preset.spells.featSpellKeys` (slug англійської назви: `bless`, `charm-person`). Для Telekinetic і
Telepathic — `featSpellKeys: []`, але блок `spells` усе одно потрібен: без нього поіменне заклинання не запишеться.
`show-catalog.ts feat <KEY>` показує правило. Інші риси із заклинаннями (`SPELL_SNIPER`, `STRIXHAVEN_INITIATE_*`,
`INITIATE_OF_HIGH_SORCERY`, `FEY_TELEPORTATION`, `WOOD_ELF_MAGIC`) пресет не записує: або вкажіть `incomplete`, або
blocked.

```json
"featOptionName": null,
"spells": {
  "classCantripKeys": [], "knownSpellKeys": [], "spellbookKeys": [], "raceSpellKeys": [],
  "featSpellKeys": ["guidance", "light", "bless"],
  "sectionId": "section-feats", "explanation": "Посвячений у магію (клірик): обрано автором…",
  "platformChoices": ["featSpells"]
}
```

Для заклинача додайте звичайні `classCantripKeys`/`spellbookKeys` у той самий блок. Один список для всіх трьох заклинань
Magic Initiate платформа не запам’ятовує — його видно з самих заклинань. `platformChoices: ["featSpells"]` ставте, якщо
автор заклинань не називає (наприклад, пише лише «Посвячений у магію»). Відомі межі: ручний конструктор і підвищення
рівня цього кроку ще не мають, на листі 2014 немає окремої КС за джерелом-рисою, відновлення «раз на відпочинок» не
відстежується.

## Підготовлені заклинання на старті, расові замовляння, Кмітливий дослідник

**Підготовка Клірика, Друїда, Винахідника (з 2026-10-10).** Якщо автор називає підготовлені заклинання 1-го рівня, запишіть їх у
`preset.spells.preparedSpellKeys` (slug англійської назви). Ліміт — модифікатор Мудрості + 1 для Клірика й Друїда, модифікатор Інтелекту
для Винахідника (на 1-му рівні половина рівня дає 0), не менше одного; правило —
`src/rules/initial-prepared-spells-2014.ts`. Кандидати — заклинання 1-го рівня зі списку класу, які персонажеві ще не дає правило:
заклинання домену чи клятви, що автор теж радить (Палючі долоні Домену світла, Божа милість Домену війни), у
`preparedSpellKeys` НЕ пишуться — вони видаються самі й не зараховуються в ліміт. Сервер відхилить такий вибір, а клієнтська перевірка
домену не знає: ловить це `check-build --db` і шарди. Якщо автор називає більше, ніж дозволяє ліміт, запишіть перші названі в межах ліміту й додайте `incomplete`.
Якщо автор не називає підготовлених, залишіть `preparedSpellKeys: []` — на листі їх можна обрати пізніше. Паладин і Слідопит на 1-му рівні заклинань не мають.
Рядки лягають як `CLASS`-заклинання з бейджем класу, підготовленими. Чарівник, як і раніше, готує з книги (`platformChoices: ["preparedSpells"]`, коли вибір не авторський).

**Расові замовляння з вибору.** Астральний ельф (Астральний вогонь: Танцюючі вогники, Світло, Священне полумʼя — кандидати враховують
і розширений список раси) і Напівельф зі спадком Місячного/Сонячного ельфа (`raceOptions: ["Замовляння"]`, замовляння зі списку
Чарівника) обираються в `raceSpellKeys`. Інші спадки напівельфа: «Ельфійське бойове навчання», «Прудконогість», «Маскування в дикій
природі», «Швидкість плавання» працюють як звичайні расові вибори; «Магія дроу» заклинань поки не видає (BUG-O49-HALF-ELF-DROW-MAGIC).

**Кмітливий дослідник і Улюблений ворог.** `classOptions: ["Favored Foe", "Deft Explorer - Canny"]`: опція «Кмітливий дослідник» додає
одну експертизу (`expertise` — рівно одна навичка з наявних, у тому числі расових) і дві мови (`languages` +2); класичний «Улюблений
ворог» додає одну мову. Якщо автор не називає навичку чи мови — вибір платформи, скажіть про це в `skillExplanation`. Групи
«Налаштування Слідопита: ворог» і «місцевість» у пресеті заблоковані для зміни, бо опції по-різному впливають на експертизу й мови.

## Власна/змінена передісторія і навичка підкласу (з 2026-10-10)

**Одна дія, одна механіка.** Правило PHB «Customizing a Background» (с. 125) — «будь-які дві навички, разом два володіння інструментами чи мовами» — і є «власна передісторія» (`backgroundKey: "CUSTOM"`),
і «змінена стандартна» (назва, особливість і речі лишаються, навички/інструменти/мови автор замінює). У пресеті це поле `backgroundCustomization`; обидва випадки пишуться однаково.

- `skills.background` — **рівно дві** навички, які автор бере від передісторії (вони замінюють усі її навички каталогу). Повторювати навичку з класу, раси чи підкласу не можна.
- `backgroundCustomization.tools` — інструменти (ключі `ToolCategory`: `THIEVES_TOOLS`, `HERBALISM_KIT`, `CARTOGRAPHERS_TOOLS`, `COOKS_UTENSILS`…), які автор бере **замість мов** передісторії. Один інструмент забирає одну мову: у Мудреця дві мови, тож
  дозволено до двох інструментів; у Воїна-Народного героя мов немає — інструмент додати не вийде. `languages` у пресеті лічить лише решту мов.
- Для `CUSTOM` обовʼязково: `backgroundCustomization` (навіть `{ "tools": [] }`) і дві навички; разом інструментів і мов — два (один інструмент → одна мова на вибір).
- Інструмент, який передісторія вже дає, не повторюється. **Прибрати** фіксований інструмент (Набір для маскування → Інструменти картографа) платформа не може: лист виводить його з передісторії (BUG-O49-BACKGROUND-TOOLS-DERIVED) — це blocked, `platform-limit`.
- Поясніть заміну в `skillExplanation`: «Автор налаштовує Мудреця… (правило PHB «Налаштування передісторії»)». Це авторський вибір, тож позначки «за вас» не потрібно; решта (мови, пара «клас чи передісторія») — вибір платформи.
- Коли каталог фіксує те, що за книгою є вибором (Агент фракції — Аналіз поведінки + навичка Інтелекту/Мудрості/Харизми; Переслідуваний; Міський мисливець за головами), використовуйте ту саму механіку й скажіть про розбіжність каталогу в поясненні (BUG-O49-BACKGROUND-CATALOG-CHOICES).
- Не плутайте з **заміною повтору**: якщо автор лише замінює навичку, яку вже дав клас чи раса (Корабельний майстер: Історія й Уважність → Акробатика й Непомітність), `backgroundCustomization` не потрібен — звичайні `skills.background` із N замінами.

```json
"skills": { "selectedClass": ["INSIGHT", "RELIGION"], "race": ["SURVIVAL"], "background": ["PERCEPTION", "ANIMAL_HANDLING"] },
"backgroundCustomization": { "tools": ["HERBALISM_KIT"] },
```

**Навичка підкласу 1-го рівня.** Домен миру (одна з Аналізу поведінки, Виступу, Переконання) і Домен порядку (Залякування або Переконання) дають вибір навички: впишіть її в `skills.subclass` (масив з однієї навички). Домен знань
працює через опції підкласу: `subclassOptions: ["Blessings of Knowledge: Arcana", "Blessings of Knowledge: History"]` (рівно дві; вони дають володіння з експертизою, а дві мови Благословення входять до `languages`). У Домену природи й магії навичка
в каталозі не записана (BUG-O49-SUBCLASS-SKILL-DATA) — такі прикладі лишаються blocked, доки власник не застосує SQL.

```json
"skills": { "selectedClass": ["MEDICINE", "INSIGHT"], "race": ["INTIMIDATION"], "background": ["DECEPTION", "PERCEPTION"], "subclass": ["PERSUASION"] },
"backgroundCustomization": { "tools": [] }
```

Приклади: `cleric-death-2014`, `cleric-knowledge-2014` (інструменти замість мов + Благословення знань), `cleric-order-2014` і `cleric-peace-2014` (навичка підкласу), `bard-spirits-2014` (Переслідуваний), `rogue-soulknife-2014` (`CUSTOM`).
Відхилення сервера перевіряє `tests/actions/background-and-subclass-skills-2014.test.ts`, правила — `src/rules/background-customization.ts`, `src/rules/subclass-skill-choices.ts`.

## Вибори платформи (позначайте!)

Усе, чого автор прямо не називає, але пресет мусить заповнити (набір для подорожей, мова, навичка «на вибір», тип зброї без вказівки, заміна навички),
— вибір платформи. Він має бути **явно названий** у поясненнях (`skillExplanation`/`equipmentExplanation`): «Набір священика та додаткову мову ми обрали за вас;
їх можна змінити.» Не приписуйте такі вибори автору; не пишіть «за авторським прикладом», якщо автор цього не казав.
Якщо автор називає кілька рівнозначних варіантів («алебарда або глефа»), візьміть перший названий і скажіть про це.

## Неповнота: blocked-специфікація

Коли приклад не виконується чинною платформою, не створюйте пресет і не вигадуйте компроміс. Запишіть
`data/rpgbot/build-specs/<articleSlug>.json`:

```json
{ "status": "blocked", "ruleset": "RULES_2014", "articleSlug": "paladin-oath-of-redemption-2014",
  "reviewedRevision": { "translationRevisionId": "…", "sourceRevisionId": "…" },
  "exampleSection": "section-example-build-apostle-of-peace",
  "reasonCode": "author-choice-not-executable",
  "reason": "Автор замінює в Шпигуна Непомітність на Атлетику; пресет записує лише заміни повторних навичок передісторії, а не довільну зміну її складу.",
  "missing": ["зміна навичок передісторії: Непомітність → Атлетика"] }
```

`reasonCode`: `needs-spells-at-level-one`, `needs-subclass-at-level-one`, `needs-higher-start-level`, `needs-multiclass`,
`needs-decisions-authoring` (пресет рівня 1 можливий, а рівні 2…N ще не описані — див. «Прогресія і мультиклас»; ставте, лише якщо статті бракує даних або автор не встиг, а не коли платформа не виконує рівень), `missing-catalog-entity`, `unofficial-content`, `author-choice-not-executable`, `platform-limit`, `other`.
`reason` — конкретна (що саме автор обирає й чому це не виконується), мінімум 30 символів; `missing` — що треба додати платформі/каталогу.
Облік (`build_ledger.py`) перетворює такий розділ на `incomplete-documented` з причиною. Спека не має мати пресета.

Відомі межі платформи на 2026-10-09:
- раси лише з `tasha`-підвищеннями (MPMM, Spelljammer, «Своя раса») — підтримано через `racialAbilityRules: "tasha"` (з 2026-10-09);
- заклинання `SPELL_SNIPER`, `STRIXHAVEN_INITIATE_*` та інших рис поза списком вище не записуються;
- експертиза в інструментах (злодійські інструменти Пройдисвіта) не підтримана моделлю листа — blocked (деталі в [catalog-data-gaps-2026-10-09.md](catalog-data-gaps-2026-10-09.md), §8);
- «Адепт метамагії» не має опцій у каталозі: метамагію риси не записуйте, додайте `incomplete` (BUG-O49-METAMAGIC-ADEPT);
- передісторії «Переслідуваний» і «Слідчий» у каталозі не збігаються з Путівником Ван Ріхтена (вибір двох навичок); дампір з іншою расою й шабля з двома лезами відсутні — дані й SQL у [catalog-data-gaps-2026-10-09.md](catalog-data-gaps-2026-10-09.md);
- вибір «будь-яка бойова зброя» тепер дозволяє й дальню (арбалет, лук), крім рядків «бойова рукопашна»/«проста рукопашна»;
- власна й змінена передісторія та навичка підкласу — підтримані (розділ «Власна передісторія…» нижче); не записуються лише *прибирання* фіксованого інструмента передісторії, зміна расових навичок і володінь (Customizing Your Origin);
- стартове золото замість набору — пресет бере стандартний набір класу (запишіть це в `incomplete` і поясненні);
- стартовий рівень вище 1 і старт в іншому класі, ніж перший клас автора, — blocked; мультиклас після рівня 1 тепер описується полем `levels`.

## Прогресія і мультиклас (рівні 2…N)

Поле `levels` у специфікації описує вибори гравця на рівнях персонажа 2…N. Компілятор перетворює його на `progression[i].decisions`
рецепта (формат `levelDecisionsSchema`), ставить `supportedLevels = [1, 2…N]` і сам рахує рівень класу. Рівні без `levels` лишаються
текстом (`details.levelPlans`), як раніше. Правил рівнів у специфікації немає: що клас дає на рівні, береться з каталогу; ви лише називаєте те,
що обирає гравець, і підтверджуєте його джерелом статті.

### Крок 1. Прочитайте таблицю рівнів статті

`bun scripts/rpgbot/show-build-source.ts <articleSlug> <exampleSection>` друкує рядки таблиці рівнів: «рівень персонажа: уміння, вибір». Для кожного
рядка 2…N випишіть: який клас бере рівень (автор мультикласить — це видно за новими умінями, напр. «Чаротворення (Паладин)» → «Магія пакту»), і що
автор **обирає** (підклас, підвищення/риса, бойовий стиль, заклинання, експертиза, виклики, маневри, вливання). Уміння, що приходять самі
(Додаткова атака, Сплеск дій), записувати не треба: рядок `{ "level": 5 }` усе одно потрібен, інакше ланцюг рівнів перерветься.

Потім `show-catalog.ts levels <CLASS>` і `subclass <CLASS>/<SUBCLASS>`: на яких рівнях класу підклас, підвищення, експертиза, які групи виборів і скільки заклинань
додає кожен рівень. Це ваша перевірка, що автор не ставить підвищення на рівень без нього. Уважно з рівнем класу: Паладин 2 на рівні персонажа 3 (після рівня Чорнокнижника) — це **2-й**
рівень Паладина.

### Крок 2. Запишіть `levels`

Масив записів `{ "level": 2 }, { "level": 3, … }`, строго підряд з 2-го рівня, без пропусків. Ключі запису (усі, крім `level`, необовʼязкові):

| Ключ | Що означає |
|---|---|
| `level` | Рівень **персонажа** (2…20) |
| `classKey` | Клас, що бере цей рівень. За замовчуванням — клас 1-го рівня, тож потрібен лише на рівнях **іншого** класу (мультиклас) |
| `subclassKey` | Підклас, що обирається саме на цьому рівні (рівень класу має дорівнювати рівню підкласу класу) |
| `abilityScoreIncrease` | `[{ "ability": "STR", "amount": 2 }]` або дві по `amount: 1` |
| `featKey` (+`featOptions`) | Риса замість підвищення: `[{ "optionNameEng": "…" }]` для рис з опціями |
| `classOptions` / `subclassOptions` | Вибори класу чи підкласу: `[{ "optionNameEng": "Dueling" }]`; у кожній групі рівно стільки, скільки вимагає рівень (Маневри Майстра бою — 3; Потойбічні виклики — 2 на 2-му); якщо назва є в кількох групах — додайте `groupName` |
| `spells` | Названі автором заклинання: `{ "cantripKeys": [], "knownSpellKeys": [], "spellbookKeys": [] }` (slug англійської назви: `booming-blade`) |
| `openSpellPicks` | Скільки заклинань автор **не називає** і обирає гравець: `[{ "category": "knownSpells", "count": 1 }]`; категорії `cantrips`, `knownSpells`, `spellbook` |
| `classOptionSpellKeys` | Заклинання, які вимагає **уміння підкласу** на цьому рівні класу (див. «Заклинання від умінь підкласу» нижче) |
| `replaceSpell` | Заміна відомого заклинання: `{ "drop": "sleep", "add": "enhance-ability" }` (див. «Заміни» нижче) |
| `replaceOptions` | Заміна раніше обраного вибору (виклик Чорнокнижника, бойовий стиль, маневр): `[{ "drop": { "optionNameEng": "Fiendish Vigor" }, "add": { "optionNameEng": "Improved Pact Weapon" } }]` |
| `expertise` | Експертиза: `["ACROBATICS", "PERCEPTION"]` (Пройдисвіт 6, Бард 3 і 10) |
| `skillProficiencies` | Навички здібності з вибором навичок (Бард Коледжу знань, 3-й: 3 навички) |
| `multiclassSkills` | Навичка, яку дає **перший рівень Барда, Слідопита чи Пройдисвіта, взятого не першим класом**: `["INSIGHT"]`. Обовʼязкова на цьому рівні; Бард бере будь-яку, Слідопит і Пройдисвіт — зі свого списку, і не ту, що персонаж уже має. Автор її зазвичай не називає: обирайте за вибором платформи й записуйте в `incomplete` |
| `infusions` | Вливання Винахідника за `engName`: `["Enhanced Defense", …]` — 4 на 2-му, по 2 на 6, 10, 14, 18-му |
| `section` | Розділ статті, на який спирається запис (за замовчуванням `levelTableSection`); вибір риси автор може пояснювати в `section-feats` |

Правила:
- **Нічого не вигадуйте.** Якщо автор не називає заклинання, лишіть `openSpellPicks`, не підставляйте своє. Квота заклинань класу обовʼязкова: компілятор знає,
  скільки замовлянь і заклинань клас дає на рівні (`show-catalog.ts levels`), і падає, якщо в `spells`+`openSpellPicks` менше або більше.
- Підвищення/риса: або `abilityScoreIncrease`, або `featKey`. Рівень підвищення, якого автор не використовує, — не помилка (буде попередження).
- Підклас класу, що вже має підклас, не повторюється; клас, що досягнув рівня підкласу без нього, — помилка.
- Харизма 19 + 2 — помилка (стеля 20): автор, імовірно, рахував інакше, звірте з таблицею.
- HP — середнє значення (кидка немає); слоти й мультикласову таблицю рахує двигун.

### Крок 3. Скомпілюйте й прочитайте діагностику

`compile-build.ts <slug> --dry-run`: помилки кажуть рівень, клас і що саме не так. Типові:

| Повідомлення | Що робити |
|---|---|
| `рівень 5 (Воїн 5): підвищення характеристик недоступне: Воїн отримує його на рівнях класу 4, 6, 8, 12, 14, 16, 19` | Підвищення стоїть не на тому рівні; перечитайте таблицю статті |
| `рівень 2 (Воїн 2): підклас CHAMPION обирається на 3-му рівні класу Воїн` / `Воїн 3-го рівня мусить мати підклас` | Поставте `subclassKey` на рівні підкласу |
| `Клас FIGHTER_2014 не має підкласу X. Підкласи: …` | Ключ підкласу з іншого класу |
| `заклинання: Оберіть замовлянь: 2 … зараз у плані …` | Не вистачає (або забагато) замовлянь/заклинань: додайте `spells` або `openSpellPicks` |
| `Немає заклинання shielld. Схожі: shield` | Опечатка в slug |
| `Опція «X» недоступна на рівні 4. Доступні: група: …` | Опції цього рівня класу; шукайте в `show-catalog.ts levels` |
| `subclassOptions: на цьому рівні є вибір опцій («Маневри майстра бою»), а в плані їх немає` | Рівень вимагає вибору — додайте `classOptions`/`subclassOptions` |
| `expertise: Оберіть рівно 2 навичок для експертизи` | Рівень дає експертизу — вкажіть `expertise` з навичок персонажа |
| `infusions: Винахідник 2-го рівня обирає 4 вливань, а в плані 0` | Додайте вливання |
| `рівень N … не має безперервного ланцюга кроків` | Рівень пропущено в `levels` |
| `мультиклас: … вимагає Харизма 13` | Лише попередження: правила підказують, не забороняють |

Потім `check-build.ts <slug>`: підсумок «Рівень N · Клас K: …» по кожному рівню з виборами й здібностями класу — звіряйте з таблицею статті по рядках.
Перевірка pure; остаточний суддя — справжній рушій підвищення в DB-шардах:

```
./scripts/local-test-db.sh status
bun run test:integration tests/actions/rpgbot-assembly-all.shard-{1..10}.test.ts -t <slug>   # або без -t: усі виконувані рецепти
```
Кожен шард створює персонажа справжнім `createCharacterFromBuild` на останньому рівні й на одному проміжному та звіряє рівні класів, підкласи, характеристики, HP,
слоти, заклинання з `learnedAtLevel`, риси, вибори, повтор з тим самим ключем і відсутність зайвих записів. Якщо рівня сервер не приймає, зменшіть кількість рівнів у `levels` до
останнього, який проходить, і запишіть решту в `incomplete` з причиною.

### Мультиклас

Рівні іншого класу мають `classKey`; клас додається з першого такого запису (на цьому рівні клас має 1-й рівень, а підклас з 1-го рівня, як у Чорнокнижника або Чародія, ставте
в тому ж записі). Рівень класу рахує компілятор. Рівні основного класу після відступу — просто `{ "level": N }`. Якщо стартовий клас не доходить до підкласу
(Tam Bush: Чернець лише 2 рівні), `subclassKey` у специфікації можна **не вказувати**, лише для класу, чий підклас не з 1-го рівня; підклас тоді береться в записах
`levels` потрібних класів. Для клірика, чародія й чорнокнижника `subclassKey` обовʼязковий.

### Приклад 1: однокласова прогресія (Воїн, Чемпіон, до 5-го рівня)

Таблиця статті `fighter-2014`: 2 — Сплеск дій; 3 — Бойовий архетип (Чемпіон); 4 — Покращення характеристик (Сила 17→19); 5 — Додаткова атака.

До (`data/rpgbot/build-specs/fighter-champion-shield-2014.json`, тільки старт): `supportedLevels: [1]`.
Після — додано поле і `"revision": 2`:

```json
"revision": 2,
"levels": [
  { "level": 2 },
  { "level": 3, "subclassKey": "CHAMPION" },
  { "level": 4, "abilityScoreIncrease": [{ "ability": "STR", "amount": 2 }] },
  { "level": 5 }
]
```
`check-build`: `Виконувані рівні 1–5 …; Рівень 3 · Воїн 3: підклас CHAMPION; здібності класу: Martial Archetype, Improved Critical (Champion)`;
`Рівень 4 · Воїн 4: підвищення: Сила +2`. Текстові `levelPlans` (1, 2, 3, 4, 8) лишилися як були.
Рівні 6–8 стаття теж описує (підвищення 19→20, Статура), але вони не додані: автор їх подає порадою, а не вибором для цього білда.

### Приклад 2: мультиклас (Hexadin, `hexadin-ancients-2014`, рівні 1–9)

Таблиця статті `hexadin-2014`: Паладин 1 → **Чорнокнижник (Відьмацький клинок) 1** на рівні 2 → Паладин 2–8 на рівнях 3–9; Дуель на 3-му, клятва прадавніх на 4-му,
Бойовий заклинатель на 5-му, Харизма +2 на 9-му. На рівні 2 автор називає замовляння Гримучий клинок і Позамежний заряд і заклинання Проклін та Щит.

```json
"revision": 2,
"levels": [
  { "level": 2, "classKey": "WARLOCK_2014", "subclassKey": "HEXBLADE", "spells": { "cantripKeys": ["booming-blade", "eldritch-blast"], "knownSpellKeys": ["hex", "shield"] } },
  { "level": 3, "classOptions": [{ "optionNameEng": "Dueling" }] },
  { "level": 4, "subclassKey": "OATH_OF_THE_ANCIENTS" },
  { "level": 5, "featKey": "WAR_CASTER" },
  { "level": 6 }, { "level": 7 }, { "level": 8 },
  { "level": 9, "abilityScoreIncrease": [{ "ability": "CHA", "amount": 2 }] }
]
```
`check-build`: `Виконувані рівні 1–9 …; на 9-му: Паладин 8 + Чорнокнижник 1`; `Рівень 2 · Чорнокнижник 1 (новий клас): підклас HEXBLADE; заклинання: …`.
Старе `incomplete` про мультиклас замінено на «Рівні 10–20 не описані статтею». Усі рівні виконуються чинними правилами, нічого не обрізано.

### Заклинання від умінь підкласу (`classOptionSpellKeys`)

Деякі уміння підкласу на своєму рівні класу просять гравця обрати заклинання, яке не входить у квоту класу. Сервер вимагає їх у `classOptionSpellIds`;
у `levels` це поле `classOptionSpellKeys` (slug англійської назви). Компілятор рахує вимогу **тими самими** правилами, що сервер
(`src/rules/subclass-feature-spell-choices-2014.ts`), тож: якщо рівень вимагає вибору, а ключів немає — помилка «Оберіть N …: <назва уміння>»;
якщо ключі стоять на рівні без такого уміння — помилка; заклинання мусить підходити списку/школі/рівню уміння й не бути в персонажа вже.

| Підклас (рівень класу) | Що обрати | Приклад |
|---|---|---|
| Коло землі, Друїд (2) | 1 замовлення Друїда | `{ "level": 2, "subclassKey": "CIRCLE_OF_THE_LAND", "classOptionSpellKeys": ["shape-water"] }` |
| Домен арканів, Клірик (1 і 17) | 2 замовляння Чарівника на 1-му; по одному заклинанню 6–9-го кола Чарівника на 17-му | на мультикласовому вході (клас 1-го рівня) — у тому самому записі, що й `subclassKey` |
| Домен природи (1), Домен смерті (1) | 1 замовлення Друїда / 1 замовлення Некромантії | те саме |
| Колегія знань, Бард (6) | 2 заклинання з будь-якого списку: замовлення або вашого кола | `"classOptionSpellKeys": ["fire-bolt", "cure-wounds"]` |
| Божественна душа, Чародій (1) | 1 заклинання 1-го кола зі «спорідненості» (Cure Wounds, Inflict Wounds, Bless, Bane, Protection From Evil and Good) | на мультикласовому вході |
| Містичний лучник, Воїн (3) | Штукарство (`prestidigitation`) або Друїдство (`druidcraft`) | `{ "level": 3, "subclassKey": "ARCANE_ARCHER", "classOptionSpellKeys": ["prestidigitation"], "subclassOptions": [ … Арканні постріли … ] }` |

Це **не** `spells`: квота класу й заклинання уміння окремі, `spells` з таким заклинанням дасть «не дає нових заклинань на вибір». Відкритого вибору (`openSpellPicks`)
для таких заклинань поки немає: інтерфейс складання не вміє їх запропонувати, тож їх має назвати автор; якщо не називає — `incomplete`.
У підсумку `check-build` вони друкуються як «заклинання від уміння: …». Рядок у базі: `origin CLASS`, `sourceName` уміння (напр. `Circle of the Land: Bonus Cantrip (2014)`), `learnedAtLevel` = рівень персонажа.
Першорівневий вибір старту (Домен знань на 1-му рівні першого класу) і далі йде в `preset.spells.classOptionSpellKeys`.

### Заміни (`replaceSpell`, `replaceOptions`)

Рушій підвищення вміє: (а) заміну **одного** відомого заклинання на рівні для Барда, Чародія, Чорнокнижника, Слідопита та третинних заклиначів
(Потойбічний лицар, Містичний спритник), (б) заміну вибору з групи, для якої клас має опціональне уміння «Замінити …»: виклик Чорнокнижника
(з 3-го рівня класу), бойовий стиль Воїна/Паладина/Слідопита (рівні підвищень), маневр Воїна, прокляття й мутагени Мисливця за кровʼю.
Замовляння 2014 не міняються (правил на це немає), заклинання Чарівника — теж (книга), заміна дисципліни Монаха — немає опціонального уміння.

```json
{ "level": 3, "classOptions": [{ "optionNameEng": "Pact of the Blade" }], "spells": { "knownSpellKeys": ["armor-of-agathys"] },
  "replaceSpell": { "drop": "protection-from-evil-and-good", "add": "blur" },
  "replaceOptions": [{ "drop": { "optionNameEng": "Fiendish Vigor" }, "add": { "optionNameEng": "Improved Pact Weapon" } }] }
```

Правила, які перевіряє компілятор: `drop` має бути в персонажа **до** цього рівня (названим, відкритим чи стартовим), `add` — зі списку класу й не вище за найвищий коло на цьому рівні, ще не наявний;
для `replaceOptions` — обидві опції з однієї групи, на цьому рівні класу є уміння заміни, `add` дозволений за рівнем (`prerequisites.level`), у групі лише одна заміна на рівень.
Пакт для викликів, що його вимагають (`prerequisites.pact`), компілятор не звіряє — це бачить DB-шард (рівень з Пактом Клинка, обраний на тому ж рівні, проходить). Звільнене заклинання можна взяти знову пізніше.
Пишіть заміну **на рівні, де автор її робить**, і окремо — нові заклинання за квотою (заміна її не зменшує).

### Знизити або прибрати рівні

Скоротити `levels` до меншої кількості можна завжди: `compile-build.ts <slug>` перезапише рецепт і надрукує «рецепт скорочено: виконувався до N-го рівня, тепер до M-го».
Прибрати `levels` повністю компілятор не дає (захист ручних рецептів), хіба що явно: `compile-build.ts <slug> --discard-levels`.
Прапор працює лише для рецептів, які зібрав компілятор; три ручні пілоти (`build-barbarian-berserker-2014`, `build-wizard-evocation-2014`, `build-sorcadin-clockwork-2014`) він не перезапише ніколи.
Видаляти файли рецептів руками не треба.

### Відкриті вибори в DB-шардах і дрейф списків

Шард бере відкриті вибори з пулу заклинань **бази** (списки класів з `spell_classes`), а не з `spells.json`: так він не пропонує те, що сервер відхиляє
(у локальній базі 15 заклинань дунамантії, напр. Gift of Alacrity, у каталозі `spells.json` числяться в списку Чарівника, а в базі — лише в школі хронургії).
Заклинання, які підклас дає сам (`data/2014/subclass-granted-spells.json`), компілятор не дозволяє ні називати, ні брати відкритим вибором на рівні, де вони вже видані;
якщо гравець уже тримав таке замовлення (Мала ілюзія Школи ілюзії), підклас забирає його собі (Р53): рядок стає `sourceName` підкласу, а звільнене місце дає одне замовлення «наздоганяння» з наступного підвищення.
Те саме робить раса (`data/2014/race-granted-spells.json`, Р53): коли персонаж доходить до рівня, на якому раса дає заклинання (Пекельна істота — Темрява з 5-го, Магія дроу — Темрява з 5-го), уже відоме заклинання Чорнокнижника стає рядком раси
(`origin RACE`, `sourceName` раси чи підраси, `excludeFromKnownCount/PreparedCount`, `learnedAtLevel` не змінюється), а наступне підвищення дає одне замовлення чи заклинання «наздоганяння». Назвати таке заклинання **після** рівня раси не можна — його вже дала раса.
Заклинання інших родів Джина (патрон «Джин») компілятор не дозволяє: Стіна каменю — лише для роду Дао.

### Вибір «будь-яка риса / підвищення / метамагія / виклик» (з 2026-10-10)

Коли автор пише «Риса: будь-яка», «Покращення Характеристик (будь-яка)», «метамагія: будь-яка» чи «потойбічний виклик: будь-який» і не називає вибір, **не зупиняйте `levels`**.
Запишіть рівень зі **типовим** вибором (його обираєте ви, помірковано: підходяща для збірки риса чи характеристика) і додайте прапор — гравець на сторінці пресета зможе змінити вибір перед створенням:

| Прапор у рядку `levels` | Що робить | Що писати як типове |
|---|---|---|
| `"openAdvancement": true` | рівень з рисою чи підвищенням характеристик, який гравець може змінити | `featKey` (+ не більше одного `featOptions`) **або** `abilityScoreIncrease` (+2 до однієї чи +1/+1 до двох) |
| `"openClassOptions": true` | вибір класу (метамагія, потойбічні виклики), який гравець може змінити | `classOptions` — рівно стільки опцій, скільки клас дає на цьому рівні |

```json
{ "level": 19, "featKey": "LUCKY", "openAdvancement": true },
{ "level": 14, "abilityScoreIncrease": [{ "ability": "WIS", "amount": 2 }], "openAdvancement": true },
{ "level": 17, "classOptions": [{ "optionNameEng": "Subtle Spell" }], "openClassOptions": true }
```

- Типова риса мусить бути простою: у пулі гравця — риси без умов і без складних виборів (Удача, Пильний, Здоровань, Стійкий, Рухливий, Вартовий…; повний перелік — `OPEN_ADVANCEMENT_FEAT_KEYS` у `src/lib/optimization/ready-preset-feat-pool.ts`). Типова риса з кількома `featOptions` не підтримана — компілятор відмовить.
- Типове завжди проходить усі перевірки (рівень, умови, непоновлюваність); гравець бачить мітку «вибір платформи: автор цього не називає», доки сам не змінить.
- Запишіть у `incomplete` один рядок на пресет: «Автор пише «будь-яка» на N-му рівні; пресет бере типову X, гравець може змінити».
- Для заклинань «на вибір» як і раніше `openSpellPicks`; для експертизи «будь-яких 2 навичок» і вибору підкласних опцій (Арканні постріли) відкритого вибору ще немає — зупиніть `levels` перед ним.
- Приклади: `fighter-cavalier-2014` (риси 16, 19), `fighter-champion-shield-2014` (підвищення 14, 16, 19).

### Що не підтримано (запишіть у `incomplete` або blocked)

Заміна замовлення чи заклинання Чарівника, заміна дисципліни Монаха (немає опціонального уміння), відкритий вибір заклинання уміння підкласу (`classOptionSpellKeys` лише поіменно), вибір мов, вибір заклинань риси на підвищенні (Magic Initiate за підвищення), перевчання Тривоги тощо, кидок HP, стартовий рівень вище 1,
школи заклинань третинних заклиначів (Лицар-чаклун, Містичний спритник) компілятор не перевіряє — це робить DB-шард. Заклинання, які підклас дає сам (клятви, домени), в `spells`
не називайте: сервер відхилить дубль (його видно лише в DB-шарді). Рівень, який сервер не приймає, лишайте за межею `levels` і поясніть причину.

- Не копіюйте текст статті у специфікацію; не вигадуйте вибір, якого автор не називає, без позначки.

- Не змінюйте існуючі пресети й рецепти, не запускайте `compile-build.ts --all` без `--verify` (запис перезапише всі файли зі специфікацій).
- Не редагуйте `ready-preset*.ts`, `build-assembly.ts`, статті, aliases, `builds.json`, облік, не комітьте.
- Вигадані «обхідні» значення (наприклад, інший клас/раса «схожі») не допускаються: або точно за автором, або blocked.

## Альтернативи автора (`initialChoices`, `choices`)

Якщо автор пропонує кілька варіантів раси, передісторії чи риси (наприклад, «Людина» або «Своя раса» з іншим підвищенням на 4-му рівні), їх можна зберегти разом із рівнями до 20-го. У специфікацію додаються два необовʼязкові поля:
- `initialChoices` — ключі виборів (`"race"`, `"background"`, `"feat"`);
- `choices` — масив тієї ж форми, що `choices` у рецепті (`choiceId`, `stage`, `sourceRefs`, `count`, `alternatives` із `levelOverrides`).

Компілятор копіює їх у рецепт без змін; валідація корпусу перевіряє ключі сутностей і посилання. Зразки: `monk-open-hand-2014`, `monk-shadow-2014`.

## Типовий вибір замість зупинки (2026-10-10, пізній вечір)

Якщо автор не називає вибір («будь-які 2 навички», вливання «на вибір», біом, опції підкласу, метамагія замість заміни), а платформа не має прапора `openAdvancement` / `openClassOptions`, у `levels` записується явно названий типовий вибір, а в `incomplete` — «вибір платформи; після створення можна змінити на листі». Зупинка потрібна лише тоді, коли компілятор відхиляє план. Навички від мультикласу (Пройдисвіт, Слідопит, Бард) платформа не дає: у таких місцях беріть експертизу й вибори з навичок, які персонаж уже має.
