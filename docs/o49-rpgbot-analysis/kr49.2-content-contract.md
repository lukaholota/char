# KR49.2 — Контракт статей, оцінок і зв’язків із каталогом

**Стан:** 🟢 завершено 2026-09-29. Контракт перевірено на власних технічних fixtures;
реальний повнотекстовий корпус і matching сутностей залишаються KR49.3.
Формат, артефакти й команди: [content-contract.md](content-contract.md).

Реалізувати [architecture.md](architecture.md): окремі повні статті, source revisions,
стабільні section IDs, контекстні ratings, optional entity bindings та маленькі індекси.
Місце нових типів і чистих helper-функцій — рекомендовано `src/lib/optimization/`.
Читач повного файлу — server-only; маленькі summary/binding типи придатні для клієнта.

## Кроки

- Визначити типи та runtime validation для source/translated articles, ratings і bindings.
  Підтвердити чинні ключі `SubclassI`, `ClassData`, `SubclassData`; не використовувати `any`
  як контракт нової інтеграції.
- Визначити допустимий content AST для headings/paragraphs/lists/tables/links/ratings.
  Перевикористати чинні засоби форматування, де вони зберігають семантику; raw HTML
  не допускається до браузера без нормалізації й очищення.
- Зробити детермінований генератор article index, binding previews і section search data.
- Додати явний resolver primary binding за редакцією та entity key, зі звітом ambiguity.
  Пошуковий lookup не має залежати від перекладеної назви чи порядку масиву.
- Source hash змінився → переклад stale, stable section IDs та published ревізія збережені.
- Закласти source refs і entity keys для BuildRecipe/choice/progression; реалізація
  recipes, UI дерева й складання — KR49.8–49.10, а не дублі контенту/правил.

## Приймання

- [x] Одна стаття може містити кілька оцінок тієї самої сутності в різному контексті.
- [x] Часткова/відсутня оцінка не перетворюється на нуль, середній бал або 4/4.
- [x] Bindings не змішують 2014/2024 й однойменні підкласи різних класів.
- [x] Стаття існує без binding; підклас може вести на comparison section.
- [x] Повторна генерація не змінює IDs; зміна назви не ламає адреси.
- [x] Invalid refs, duplicate primary binding та edition mismatch дають явний звіт/помилку.
- [x] Новий корпус не потребує DDL чи DB-запитів у build/runtime.

Змістовні перевірки: fixtures з conditional ratings, no-rating, comparison-only,
missing entity, legacy та revision update. Перевірити import graph: повний article reader
і корпус не потрапляють у client registry чи root layout. Production-код перед завершенням
переглянути через `clean-code-guard`.
