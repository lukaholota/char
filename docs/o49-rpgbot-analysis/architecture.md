# O49 — Контракт контенту й поведінка читання

**Стан:** рекомендована специфікація для KR49.2; 2026-09-28. Це план, не існуючі моделі.

## Зберігання та доставка

Аналітика — статичний контент. Початково не потрібні таблиці PostgreSQL, DDL чи сіди.
Рекомендовані шляхи: `data/rpgbot/manifest.json`, `data/rpgbot/source/`,
`data/rpgbot/uk/`, `data/rpgbot/bindings.json`; генеровані індекси —
`src/lib/generated/optimization-*.json`. Сирий корпус додається лише після закриття
залежності джерела. Не підміняти ним тексти правил у наявних каталогах.

Повні статті зберігати окремими файлами, а не одним гігантським JSON. Серверний читач
віддає потрібну статтю. Невеликий індекс містить назви, теми, редакцію, розділи й адреси.
Пошуковий артефакт містить потрібний текст для пошуку по розділах, але без HTML,
повторів легенди та решти оформлення; завантажується тільки для пошуку.
Компактний індекс прив’язок і витягів модалок не імпортує весь корпус.

Детермінований генератор звіряє записи й створює артефакти без мережі під час build.
Підтримати чинні рішення [Р23](../DECISIONS.md#р23), [Р25](../DECISIONS.md#р25) та
обмеження ваги [O46](../o46-js-weight/README.md). Секрети й персональні дані не потрібні.

## Основні записи

| Запис | Обов’язкові поля та семантика |
|---|---|
| `SourceEntry` | Стабільний `sourceId`, requested/final/canonical URL, aliases, status `included / excluded / review`, причина, edition evidence, тип матеріалу, дата перевірки; дозвіл/походження корпусу — посилання на evidence |
| `SourceRevision` | `revisionId`, `sourceId`, дата отримання, source updated date за наявності, hash повного тексту, автори, назва, шлях до повного джерела; HTTP validator за наявності |
| `AnalysisArticle` | Стабільний `articleId`, `slug`, явний `Ruleset`, українська й англійська назви, теми, active published revision за наявності; стан публікації `unpublished / published` |
| `ArticleTranslationRevision` | `translationRevisionId`, `articleId`, `sourceRevisionId`, `draft / reviewed / stale`, дата перевірки, впорядковані sections; оновлення джерела не видаляє попередню published revision |
| `AnalysisSection` | Стабільний `sectionId`, parent section за потреби, heading, блоки повного тексту, lists/tables/links, inline rating references; source anchor зберігається окремо |
| `AnalysisRating` | `ratingId`, `articleId`, `sectionId`, точний rated block/option, `score: 1 / 2 / 3 / 4`, вихідний колір, контекст, пояснення або посилання на його блок; entity target необов’язковий |
| `EntityBinding` | `Ruleset`, `kind`, чинний entity key, parent key для гілок; `articleId`, `sectionId`, роль `overview / comparison / dedicated`, primary flag; доказ ручної звірки |
| `AnalysisPreview` | Посилання на статтю/розділ/translation revision, короткий перевірений витяг, applicable rating references, посилання «Читати повний аналіз»; жодних власних оцінок |

Типи сутностей для bindings: class, subclass, race, subrace/variant, feat, background,
spell, magicItem, feature. Це можливості контракту, а не вимога додати всі їхні
аналітичні модалки в O49. На початку обов’язкова UI-проводка лише subclass.

`Ruleset` використовувати чинний (`RULES_2014` / `RULES_2024`). URL дає кандидата редакції,
а підтвердження походить із тексту статті. Суто спільний матеріал може мати дві явні
публікації з перевіреною застосовністю, які посилаються на одну source revision;
це не автоматичне дублювання чи наслідування оцінок.

`articleId` не змінюється від перекладу заголовка або редиректу source URL.
`sectionId` не виводиться заново з українського заголовка після кожної правки.
Переміщення джерела й перейменування розділу зберігають aliases старих посилань.
Оновлення джерела створює нову ревізію; reviewed переклад позначається stale до звірки,
не перезаписується повторним краулінгом. Published версія лишається доступною з датою.

## Оцінки та їхній контекст

Внутрішнє відображення шкали RPGbot: red → 1, orange → 2, green → 3, blue → 4.
Кольоровий маркер доповнюється числом `N/4` і текстовим підписом, щоб не залежати
від розрізнення кольорів. Значення шкали перекладаються й перевіряються за словником.
Джерело шкали: [Fighter 2014](https://rpgbot.net/dnd5/characters/classes/fighter/).

Зберігати оцінку саме того об’єкта, який оцінив автор: підклас, його окрему рису,
заклинання або опцію в контексті класу/білда. Нерейтингова кольорова розмітка не є
оцінкою. Порівняння підкласів може мати загальну оцінку, окрема стаття — оцінки рис.
Різні контексти мають окремі записи, не усереднюються в число «сила підкласу».

Якщо оцінки всього підкласу немає, показати перевірений витяг і посилання без числа.
Якщо джерело дає умовні або декілька оцінок, показати умови поруч. Не переносити
оцінку 2014 в 2024 та не видавати advice зі старої статті за адаптацію правил 2024.

## Прив’язки

Каталогові `ClassData` / `SubclassData` вже мають `key`; subclass прив’язується через
`Ruleset + parent class key + subclass key`. Числовий DB ID — лише чинний runtime
ідентифікатор вибору, не канонічний ключ статті. Адаптер для constructor `SubclassI`
використовує його чинний enum key та редакцію батьківського класу, перевірені в KR49.2.
Не порівнювати лише українську назву чи слуг підкласу без батька та редакції.

Одна сутність може мати dedicated статтю, розділ порівняння й згадки в інших гайдах.
Редактор задає primary binding; інші залишаються додатковими посиланнями.
Підклас без окремої статті може відкривати свій розділ comparison guide.
Стаття про відсутню сутність лишається читабельною; binding є optional.

Для legacy у 2024: автоматичного fallback до 2014 немає. За відсутності аналізу
2024 допустиме окреме явно підписане посилання «Аналіз за правилами 2014»;
його оцінки не відображаються як актуальні 2024. Чинний [Р52](../DECISIONS.md#р52)
про каталог і пошук legacy не змінюється.

## Стаття й модалка

Статті: `/optimization/[slug]` і `/2024/optimization/[slug]#sectionId`.
Каталог має категорії/теми, фільтр редакції через чинну навігацію, українські назви,
пошук і автора; повний текст — зміст, розділи, таблиці, оцінки, внутрішні переходи,
видимі оригінал/автор/дата звірки. Посилання на правила ведуть до нашого каталогу
правильної редакції; відсутній відповідник лишається зовнішнім посиланням.

У модалці після назви та редакції, перед лором і механічними описами:
блок «Аналіз RPGbot», applicable оцінка за наявності, короткий витяг із поясненням
і контекстом, «Читати повний аналіз», додаткові related guides за наявності.
Для catalog `BranchReader` потрібен окремий слот перед `CatalogProse`;
дописування аналізу в `description` змішало б лор і статтю та продублювало контент.

«Читати повний аналіз» відкриває відповідний розділ у тій самій читальній модалці,
зі збереженим станом підкласу й кнопкою «До підкласу». Це явно відкритий повний текст,
який довантажується після дії, а не друга вкладена модалка. Окреме посилання
«Відкрити статтю» дає канонічну сторінку. Прямий URL статті працює незалежно від білдера.
Перехід назад відновлює скрол; закриття відновлює фокус тригера.

У конструкторі читання не записує вибір і не змінює форму. Повернувшись до підкласу,
гравець обирає його чинною карткою. Зі статті й аналітичного блоку також доступний
явний CTA «Зібрати цей варіант», якщо є перевірений BuildRecipe. Він відкриває дерево
з відповідними початковими виборами; draft змінюється після явного застосування результату.

## Структуровані варіанти та білди

Статичні recipes рекомендовано зберігати у `data/rpgbot/builds/`; generated index
містить класи/білди без повних статей. Recipe — перевірені ключі, вибори й умови
із source revision/section/block, а не вільний текст для LLM-інтерпретації при кліку.

| Запис | Контракт |
|---|---|
| `BuildRecipe` | `buildId`, revision, Ruleset, title, source refs, starting class key, supported level range/snapshots, initial choices, ordered progression, recommendation groups, coverage status |
| `BuildChoiceGroup` | ID, етап, required count, source-backed alternatives, rating refs і пояснення, залежності від попередніх виборів |
| `BuildProgressionStep` | Character level, class key і class level, `decisions` (subclass/feat/ASI/spell/option цього рівня), `openSpellPicks` для невизначених виборів; крок без `decisions` не виконуваний (див. KR49.10) |
| `BuildDraft` | Ruleset, recipe revision, target starting level, alternatives і власні зміни, validation issues; окрема client draft |
| `BuildAssemblyPlan` | Повний стартовий `PersFormData`, ordered level-up inputs до target level, unresolved picks, current/future equipment, recipe refs; поки не DB-запис |

Два типи: авторський example build і дерево альтернатив, які RPGbot прямо рекомендує
в контексті класу/підкласу. Другий тип позначається як поєднання запропонованих варіантів,
а не новий готовий авторський білд. Не генерувати рекомендацій чи рейтингу комбінації
від імені RPGbot. Unspecified поле лишається вибором гравця; механічну сумісність
перевіряють чинні правила, а не число рейтингу.

Coverage ledger окремо рахує source example builds і recommendation groups:
mapped, incomplete, unavailable entity, reviewed executable. Missing entity показує
конкретну незавершену частину; стаття лишається читабельною. Не підставляти непомітно
«найближчий аналог». Повний перелік прикладів із корпусу має мати disposition;
статус executable вимагає усіх необхідних source/entity matches.

## Дерево вибору

Вхід із меню або статті: редакція → клас із наявним зображенням → підклас/конкретний
example build → решта гілок. Показуються source-backed рекомендації, залежності,
оцінки й «Чому цей варіант» із переходом до source section. На телефоні те саме дерево
має вертикальне компонування. Це не генерація всіх можливих комбінацій D&D.

Поля: раса/підраса, походження, характеристики й бонуси, навички/мови, стартові
риси/опції, заклинання, класові вибори, спорядження; окремо — мультикласовий шлях,
ASI/риси й заклинання наступних рівнів. Видима різниця «отримую на обраному рівні»
та «планую пізніше». Можна змінити рекомендацію на іншу підтриману сутність.

Зміна батьківського вибору перераховує залежні вузли й зберігає незалежні налаштування.
Несумісні вибори показуються для виправлення. Повернення зі статті зберігає BuildDraft.
Named builds знаходяться через пошук та мають URL із buildId/revision, які відновлюють
вихідний рецепт; користувацькі зміни зберігаються в чернетці своєї редакції.

## Збирання персонажа

«Зібрати персонажа» створює BuildAssemblyPlan і заповнює чинний конструктор.
Якщо вибори завершені — фінальний перегляд і крок імені; інакше дообрати конкретні
навички/заклинання/опції. Схеми й правила — ті самі, що для ручного create/levelup.
`creation-step-completion.ts` перевіряє частину полів поверхово: його boolean придатні
для навігації, але не є достатньою валідацією нового submit. Перевіряти повні counts
та selections, зберігаючи чинну політику попереджень про prerequisites.

Перегляд статті/BuildDraft не перезаписує чернетку ручного конструктора. Після явного
застосування нового білда можна повернути попередню чернетку. Редакційні storage keys,
level-up draft і sheet draft не змішуються. Запис персонажа — лише після підтвердження.

Поточний `createCharacter` зберігає classLevel 1. Для вищого стартового рівня потрібна
серверна координуюча операція з reuse `character-creation`/`levelup-persistence`
та правил: стартовий рівень, потім кожен progression step у належному порядку.
Підстановка тільки `pers.level` чи майбутньої риси в стартові поля не збирає білд.
Перед змінами зробити characterization чинних шляхів; не переносити їхні правила
в новий клієнтський білдер.

Рекомендовано один server request і транзакцію всіх кроків до target level,
без мережевих звернень до статей. KR49.10 спершу перевіряє можливість transaction reuse.
Частковий персонаж не видається за готовий білд; повтор submit не створює дубля.
Цикл клієнтських level-up actions після create не є готовим виконанням контракту.
Server звіряє keys, редакцію, правила й користувача, не довіряє довільному клієнтському плану.

Стартове спорядження заповнюється за правилами/вибором користувача. Майбутні магічні
предмети з guide лишаються рекомендаціями, а не автоматичним стартовим інвентарем.
Ефект складання з початкової ідеї запускається після дії, підтримує reduced motion
і не приховує незавершені вибори.

Статичним рецептам DB-таблиці не потрібні. Якщо потрібна постійна метаінформація
користувацького плану/складання, спочатку перевірити чинну схему; DDL — за процедурою
SQL → власник застосовує → db:pull. Це не підстава створювати окрему контентну DB.

## Оновлення

Синхронізація запускається окремим tooling command, ніколи на читачевому запиті.
Manifest має preview/diff; недоступна сторінка, змінена оцінка або невпізнаний блок
створюють звіт для перегляду. Старий переклад не видаляється через мережеву помилку.
Видалення статті з публікації — явна редакційна дія з redirect/alias за потреби.
Без автоматичного background cron у першій реалізації.
