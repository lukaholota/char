# Аудит мобільного UX — 2026-10-11

Запит власника після прогону на iPhone (Safari і встановлений застосунок через dev-тунель):
подвійні натискання, відсутній відгук, офлайн-лист не переживає перезавантаження, «Назад»
активний без куди повертатися, пропозицію встановлення не бачать новачки, інструкція iOS
не збігається з Safari, blur угорі екрана.

Запит розширює межу O50: тепер воркер зберігає ще й сторінки, відкриті повз нього
(перший візит і клієнтські переходи). Логіку офлайн-черги не змінено.

## Перевірене середовище

Production-збірка (`next build` + `next start`) копії робочого дерева на окремій тестовій базі,
Playwright Chromium з емуляцією Pixel 7, CPU ×4. Порівнюються «до» (робоче дерево) і «після»
(те саме дерево плюс лише ці правки). Фізичний iPhone і справжній iOS Safari **не перевірено**:
WebKit на macOS не має механізму iOS, що спричиняє подвійний тап.
Артефакти — [evidence/mobile-ux-audit](evidence/mobile-ux-audit/).

## Причини й виправлення

| Проблема | Причина | Виправлення |
|---|---|---|
| Подвійний тап | Tailwind 3 застосовує `hover:` і на дотику. `OrnateFrame` на hover проявляє світіння з `opacity-0`; iOS Safari вважає тап, що робить вміст видимим, наведенням і не надсилає click. Попередня сесія обійшла це лише для «Персонажів» повним перезавантаженням сторінки (`navigateOnFirstTouch`) | `future.hoverOnlyWhenSupported`: усі hover-стилі лише для `(hover: hover) and (pointer: fine)`. Обхід видалено. Кнопки «+» у діалогах зброї й обладунку на дотику тепер видимі |
| Немає відгуку | Той самий обхід: `location.assign` заморожував стару сторінку до відповіді сервера. Індикатор переходу в панелі — спінер 3×3 px | Клієнтський перехід зі скелетом `loading.tsx`. Вкладка панелі підсвічується одразу під час переходу, `:active` дає миттєвий відгук. Картка головної показує спінер |
| Офлайн: перезавантаження листа | HTML кешувався лише для навігацій через воркер. Перший візит іде до того, як воркер бере сторінку під контроль, а клієнтські переходи Next (RSC) воркер не зберігає | Повідомлення воркеру `save-for-offline`: зберегти HTML сторінки й уже завантажені файли. Лист після відкриття зберігає себе, прогріває ліниві вкладки й картки заклинань; після правок онлайн знімок оновлюється (через 10 с, лише з порожньою чергою). Список персонажів зберігається при кожному відкритті |
| Офлайн під час тесту на тунелі | `dev:phone` — це `next dev`; воркер реєструється лише в production. Без нього офлайн неможливий узагалі | `bun run phone:prod` — production-збірка на тому самому порту для тунелю |
| «Назад» без куди повертатися | У standalone без власної історії кнопка робила `router.replace` на поточну ж сторінку | Вимкнена, якщо історії немає і ми вже на списку персонажів |
| Новачок не бачить установки | Банер лише на `/char/home`, а без персонажів сторінка редіректить у конструктор | Той самий банер (з другого візиту, ховається на 30 днів) — і на головній. Пункт у «Меню» лишився |
| Інструкція iOS | Загальні формулювання без реальних назв пунктів Safari 26+ | Нумеровані кроки: «•••» або затиснути адресний рядок → «Поширити» → «Переглянути ще» → «На початковий екран» → «Додати» |

Побічна регресія, знайдена й виправлена під час перевірки: лічильник візитів банера (`char:install-visits:v1`)
вмикав «Що нового» новачку на першому ж візиті, бо будь-який ключ `char:` вважався ознакою повернення.

## Заміри, медіана з 5 прогонів (localhost)

| Перехід | Відгук до → після, мс | Вміст до → після, мс |
|---|---|---|
| Головна → «Персонажі» (картка) | 225 → 94 | 269 (повне перезавантаження) → 455–510 у DOM |
| Нижня панель → «Персонажі» | 181 → 48 | 243 (повне перезавантаження) → 139 |
| Список → лист | 78 → 76 | 860 → 860 |
| Нижня панель → «Головна» | 50 → 55 | 158 → 138 |
| «Кубики» → лоток | 91 → 68 | 131 → 103 |

«Відгук» — перша зміна DOM після тапу (для повного перезавантаження — перший кадр нової сторінки).
На localhost повне перезавантаження показує текст першого відкриття списку раніше: сервер
поруч, а стара сторінка ~225 мс заморожена й потім ще гідрується. На тунелі й мобільній мережі
ціна перезавантаження зростає разом із HTML і повторним виконанням усього JS; емуляція мережі
в Playwright запитів через воркер не сповільнює, тож це не виміряно. Playwright під CPU ×4
показує вміст із запізненням до ~450 мс: час появи вимірювати з самої сторінки (MutationObserver).

## Офлайн, до → після

| Сценарій | До | Після |
|---|---|---|
| Перший візит листа, 3 або 15 с, без мережі: вкладки | працюють | працюють |
| Перезавантаження листа без мережі | не відкривається | відкривається, усі 4 вкладки працюють |
| Головна → персонажі → лист клієнтськими переходами, без мережі: перезавантаження листа | не відкривається | відкривається |
| Той самий шлях: список персонажів без мережі | відкривається (через повне перезавантаження обходу) | відкривається |
| Лист відкрито напряму, списку онлайн не було: список без мережі | не відкривається | не відкривається — очікувана межа |
| Індикатор | немає | «Зберігаю для офлайну…» → «Доступний офлайн» за ~1,2 с; «Офлайн не збережено» при збої |

## Що гарантовано без мережі

Після «Доступний офлайн» — той самий лист: відкриття й перезавантаження, усі вкладки, картки
заклинань персонажа, правки через офлайн-чергу. Список персонажів — якщо його відкривали онлайн.
Кубики — числовий запасний режим. 3D-кубики — лише якщо лоток відкривали онлайн.
Не працюють офлайн: інші персонажі, яких не відкривали; каталоги й правила, яких не відкривали;
створення персонажа, підвищення рівня й інші серверні дії поза офлайн-чергою. Кеш обмежено
60 сторінками й 600 файлами оболонки; нестача місця дає «Офлайн не збережено».

## Не перевірено й залишки

- Фізичний iPhone: подвійний тап, точні назви пунктів Safari, blur. На головній нагорі немає
  жодного елемента з `backdrop-filter`. Під статус-бар заїжджає прокручений документ — у Safari iOS 26
  це, найімовірніше, системний ефект краю. На листі нагорі є власна напівпрозора шапка з
  `backdrop-blur`. Потрібен знімок і уточнення: Safari чи встановлений застосунок.
- Кубики на тунелі: кнопка — `button`, до гідрації тап губиться. У production лоток відкривається за ~100 мс.
- Кожне відкриття листа чи списку клієнтським переходом додає один серверний рендер HTML для
  офлайн-знімка; кожна серія правок онлайн — ще один.
- Повний `test:no-db`: 23 падіння в чужих поточних тестах rpgbot/optimization (таймаути). Тести,
  зачеплені цими правками, зелені.

## Затискання картки головної — 2026-10-12

Власник у застосунку: затиснута картка чорніє, «їздить» за пальцем, на мить стає горизонтальною
й лишає сліди на сусідніх картках. Це системний знімок посилання для попереднього перегляду чи
перетягування: рамка з `clip-path` і `drop-shadow` у ньому малюється неправильно. Картка тепер
`draggable={false}`, `select-none`, `-webkit-touch-callout: none`; обкладинка — `draggable={false}`.
Миттєвий відгук `active:brightness-125` замінено на `active:opacity-80`: фільтр на посиланні
змушував заново малювати рамку з `drop-shadow` і розмитим сяйвом, а прозорість лише компонується.
Перший тап у Playwright Chromium (Pixel 7, CPU ×4–×6, затримка 250 мс, тап від 0 до 3 с після
завантаження) не губиться на збірці 08:34. На пристрої не перевірено.

## «Заклинання» з другого тапу — 2026-10-12

Власник (iPhone 14 Pro Max, збірка на тунелі): «Заклинання» й «Персонажі» приблизно в половині
випадків відкриваються з другого тапу, малі картки — з першого. Причина не в дотику: префетч
малих каталогів приносить усю сторінку (`/races` 354 КБ), а `/spells` динамічний
(`await searchParams` для старого `?selectedSpellId=`) і без `loading.tsx` — префетч 205 байт,
після тапу ще 1,15 МБ RSC (288 КБ gzip). Стара сторінка стоїть секунди, видно лише дрібний спінер
картки; другий тап «миттєвий», бо дані вже прийшли. Додано `loading.tsx` зі `SpellListSkeleton`
для обох редакцій: на 400 мс / 150 КБ/с скелет за 121 мс, список за ~3 с; модалка заклинання
зі списку скелет не показує. «Персонажі» вже мають скелет; на тунелі з входом сервер ходить
у прод-базу через тунель — на пристрої після цієї правки не перевірено.
Симулятор iOS 27 через `safaridriver` для тапів ненадійний: дотики доходять, `click` ні — навіть
на контрольних картках.

### Причина знайдена журналом дотиків

Тимчасовий журнал ([tap-debug-journal.md](tap-debug-journal.md), з коду прибрано) на iPhone 14 Pro Max
(iOS 18.7): кожен мертвий тап — `touchstart`/`touchend` без зсуву (0 px, 23–81 мс), але iOS не шле ні
`mousedown`, ні `click`. Усі мертві тапи — у перші 0,26–0,97 с після появи головної; пізніші проходять
з першого разу. Це спостерігач змін вмісту iOS Safari: поки на сторінці щось стає видимим, тап
вважається наведенням. Вхідна анімація проявляла картки з `opacity: 0` каскадом ~1 с. Варіант «лише зсув» прибрав
мертві тапи, але власник відкинув вигляд. Тепер анімація та сама, лише стартує з
`TAPPABLE_HIDDEN_OPACITY = 0.01` (`src/lib/tappable-entrance.ts`): WebKit вважає прихованим тільки
`opacity == 0`. Головна, футер, хаб правил; запобіжник `tests/content/entrance-motion-keeps-taps.test.ts`.
Із 0,01 власник побачив рвану анімацію: iOS тепер малює тіні й `clip-path` усіх карток у кожному кадрі,
а з 0 пропускав. `useEntranceLayers` дає кореню й блокам `data-entrance-layer` власні шари
(`will-change`) лише до кінця входу; на пристрої не перевірено. Тоді ж модалка каталогу перестала
фокусувати перше поле: поле коментаря тепер рендериться одразу й відкривало клавіатуру. Скелет `/spells` лишається як відгук.
Підтвердження на пристрої після правки — повторним журналом.
