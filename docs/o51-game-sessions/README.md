# O51 — Ігрові кімнати: спільний журнал кидків партії

**Стан:** реалізовано локально 2026-11-01, не в production. Потрібен SQL власника (нижче).
**Відкрито** 2026-11-01 за завданням власника «Multiplayer Game Sessions для Holota».

## Що отримує гравець

- `/games` — мої кімнати (активні й архів), створення кімнати. Пункт «Ігрові кімнати» в меню.
- `/games/[id]` — кімната: куди йдуть мої кидки й хто їх бачить, журнал, мій персонаж, учасники
  з позначкою «у мережі», запрошення (майстер), перейменування, архів і відновлення, вихід (гравець).
- `/games/join/[token]` — запрошення. Без входу — вхід Google з поверненням на ту саму адресу.
- Активна кімната памʼятається на пристрої (`localStorage`, переживає перезапуск PWA) і щоразу
  перевіряється сервером: вилучили, видалили чи заархівували — кімната вимикається з тостом.
- Кидки з листа персонажа (лише власного, не read-only і не публічного) і вільні кубики йдуть
  у журнал. Ціль («У кімнату X») і видимість (Усім / Майстру) видно в лотку до кидка; у лотку вільних кубиків гравець ще може
  обрати «Секретно» — кидок, результат якого бачить лише майстер (див. «Модель довіри»).
  Без активної кімнати кубики працюють як раніше, код журналу навіть не вантажиться.
- Журнал: гравець і персонаж, мітка, значення кубиків (відкинутий к20 закреслено), перевага чи
  перешкода з джерелами, додаткові кубики з джерелами, бонус, сума, «Природна 20/1», СК і
  результат, «надіслано пізніше» для кидків з черги. Сторінки по 50, «Нові кидки: N» замість
  автопрокрутки, коли гравець гортає історію; останній кидок озвучується `aria-live`.
  Новий кидок вʼїжджає знизу, як повідомлення в чаті (без руху за `prefers-reduced-motion`), чужий —
  з тихим синтезованим «бульком» (Web Audio, без файлу; вимикач у журналі памʼятається на пристрої).
- Свій кидок не чекає сервера: «кидає…» зʼявляється в момент натискання, результат — у тому ж кадрі,
  що й у лотку; відповідь сервера чи потік замінюють його справжнім кидком (за міткою й сумою, без
  повторної анімації), відмова кімнати прибирає його з тостом.
- «Кидає…»: щойно учасник кинув кубики, інші бачать картку з кубиком, що крутиться, доки 3D-кидок
  не осяде й не прийде результат (або 8 с). Сигнал ефемерний — лише NOTIFY, у базу не пишеться;
  потік шле його тим, кому дозволено бачити такий кидок (для «Секретно» — майстрам), а старий `SELF` не сигналить узагалі.
- Сторінка кімнати — дашборд на весь екран. Телефон: вкладки «Мапа / Герой / Журнал / Кімната».
  Від `lg`: мапа ліворуч, праворуч колонка 26rem з вкладками «Герой / Журнал / Кімната». Від 1700px:
  мапа, журнал окремою колонкою й «Герой / Кімната». У шапці — «Кидати сюди / Кидки йдуть сюди».
  Сцени відкриваються діалогом із кнопки над мапою, бій — смугою над мапою, розмір токенів та імена
  налаштовують у «Вигляд».
- «Герой» — вбудований лист привʼязаного персонажа (RSC-слот у Suspense, монтується при першому
  показі). Без персонажа гравець тут обирає героя. Майстер без героя вкладки не має.
- Поза кімнатою журнал лишається як був. На десктопі це плаваюча панель «Журнал кімнати» зліва внизу.
  На телефоні це кнопка «Журнал» над нижньою навігацією, яка відкриває bottom sheet на 70dvh.

## Як це працює

| Частина | Де |
|---|---|
| Таблиці `game_session`, `game_session_member`, `game_roll_event` | [SQL](../../db/changes/2026-11-01-game-sessions.sql) |
| Перевірка кидка (форма, ліміти, сума) | `src/rules/game-roll.ts` |
| Кімнати, членство, запрошення, видимість у запитах | `src/server/db/game-sessions.ts`, `game-roll-events.ts` |
| LISTEN/NOTIFY-хаб на процес | `src/server/db/game-session-signals.ts` |
| SSE-потік, POST кидків, сигнал «кидає…» | `src/app/api/game-sessions/[id]/{stream,events,rolling}` |
| Клієнт: потік, черга, публікація з кубиків | `src/lib/components/game/` |
| UI | `src/components/games/`, `src/app/games/` |

- **Postgres — джерело правди.** NOTIFY лише будить потік; кожне пробудження перечитує події
  з бази від курсора з фільтром видимості. Загублений сигнал не губить кидок. Redis/Kafka немає.
- **Порядок і дублікати.** `seq` видається під `FOR UPDATE` рядка кімнати — неперервний і
  монотонний у кімнаті. Унікальність (кімната, автор, `idempotency_key`): повтор повертає вже
  записаний кидок. Клієнт зливає події за `seq`.
- **Потік.** `fetch` + ReadableStream (не EventSource — потрібні статуси 401/403). Перша сторінка
  на старті, далі лише нові; пінг кожні 20 с, потік живе ≤10 хв і перепідключається сам.
  Курсор рухають лише події потоку, не відповідь на власний POST — інакше пропущені чужі кидки
  загубилися б. Повтор: `min(30 с, 1 с·2^n)·(0,5…1,5)`; тиша 45 с — перепідключення;
  прихована вкладка закриває потік через 30 с (iPhone не тримаємо живим), `visibilitychange`,
  `pageshow`, `online` — одразу назад з догоном від курсора.
- **Черга кидків** у `localStorage`, спільна для вкладок: без мережі кидок чекає до 10 хв і
  надсилається з позначкою часу кидка; 4xx (крім 401/429) і прострочені — тост «не дійшов».
- **Ціль фіксується в момент кидка**, не після анімації: перемикання кімнати в іншій вкладці
  посеред кидка не відправить його не туди.
- **Вільні кубики без подвійної публікації:** докинутий кубик публікується сам, повторний
  кидок пулу — увесь пул; очищення пулу скидає памʼять опублікованого.

## Модель довіри

Значення кубиків рахує браузер гравця, сервер перевіряє лише форму (грані з дозволеного набору,
значення в межах граней, ≤50 кубиків, сума збігається з кубиками й бонусом) і що автор — учасник
неархівної кімнати, а персонаж — його. Гравець, що підробляє запити, може записати будь-яке
правдоподібне значення: як і за столом з фізичними кубиками, журнал довіряє гравцям, а не доводить
чесність. Серверний генератор — окреме рішення, якщо партії попросять.

**Видимість — серверне право.** `PUBLIC` бачать усі учасники, `GM` — автор і майстри, `SECRET` —
майстри повністю, а автор лише запис «Секретний кидок · 1к20» без граней і суми (сервер замінює
мітку формулою й віддає `roll: null, total: null` в усіх читаннях і у відповіді на POST; інші гравці
подію не отримують). `SECRET` обирається лише в лотку вільних кубиків перед кидком (стан живе, поки
лоток відкритий, ніколи не стає типовим для кімнати), не для кидків з листа й не для майстра (для
нього це «Майстру»); у браузері автора 3D-кубики й сума ховаються, а локальний запис у журналі
показується без значень. Значення кубиків усе одно рахує браузер автора, тож це правило столу, а не
захист від підробленого клієнта (див. вище). `SELF` більше не обирається, але збережені події з ним
лишаються видимими лише автору; збережений типовий `SELF` читається як `GM`. Фільтр стоїть у SQL кожного читання (потік, сторінки, догін); приховані кидки не
потрапляють ні у відповідь API, ні в SSR (сторінка кімнати не віддає подій узагалі), ні в кеш
(`Cache-Control: no-store, private`). Логи не містять міток і значень кидків — лише назви помилок.

## Ліміти

12 учасників у кімнаті, 30 активних кімнат на власника, назва ≤80, 30 кидків і 30 сигналів «кидає…» за 10 с, 8 потоків
на користувача, тіло POST ≤16 КБ. Ліміти частоти — у памʼяті процесу (`shortcut:` у коді).

2. Звичайний деплой з `main`. Нових змінних оточення немає.
   **Мапа сцени (2026-11-05):** [db/changes/2026-11-05-game-map.sql](../../db/changes/2026-11-05-game-map.sql)

   **Секретний кидок (2026-11-06):** [db/changes/2026-11-06-game-roll-secret.sql](../../db/changes/2026-11-06-game-roll-secret.sql)

3. **nginx міняти не треба:** потік шле `X-Accel-Buffering: no` і пінг кожні 20 с — менше за
   стандартні 60 с `proxy_read_timeout`. Якщо колись журнал запізнюватиметься пачками, перевірте
   `proxy_buffering` для `location /api/game-sessions/` (готовий блок нижче, не застосовано).
4. Під час перемикання слотів старий контейнер обриває потоки на `docker stop`, клієнти
   перепідключаються з догоном від курсора; NOTIFY ходить через спільну базу, тож обидва слоти
   будять одне одного.

```nginx
# Не застосовано — лише якщо потік буферизується.
location /api/game-sessions/ {
  proxy_pass http://char_app;
  proxy_http_version 1.1;
  proxy_set_header Connection "";
  proxy_buffering off;
  proxy_read_timeout 120s;
}
```

Кожен процес тримає одне додаткове зʼєднання з Postgres для LISTEN.

## Аналітика

PostHog: `game_session_created`, `game_session_joined`, `game_roll_published` (джерело, видимість,
к20 — без міток і значень). Вхід з кімнати — `auth_requested` з тригером `game`.

Клієнтські події (`src/lib/monitoring/game-analytics.ts`, без назв кімнат, міток і значень):
`game_room_viewed` (роль, учасників, архів, чи є персонаж), `game_roll_target_changed` (увімкнув чи
вимкнув кидки в кімнату), `game_roll_visibility_changed` (видимість і де: кімната, док, лоток),
`game_pers_bound`, `game_sheet_opened` (шапка чи картка), `game_journal_opened` (телефон чи десктоп),
`game_invite_copied`, `game_invite_rotated`, `game_sound_toggled`, `game_roll_dropped` (відхилено чи
прострочено), `game_session_archived`, `game_session_left`, `game_member_removed`.

Питання, на які вони відповідають: чи доходять кімнати до другого учасника (`created` → `invite_copied`
→ `joined`), чи кидають у кімнату взагалі (`roll_published` на кімнату), чи гравці привʼязують
персонажа й ходять у лист з кімнати, чим користуються — «Усім» чи прихованими кидками, чи вимикають
звук, як часто кидки губляться.
