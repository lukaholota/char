### Родина А — застарілий Server Action ID переживає деплой (3 issue)

| Issue | Маршрут | count | Вікно |
|---|---|---|---|
| `JAVASCRIPT-NEXTJS-S` (142207720) | POST /page | 9 | 2026-08-22 → 2026-08-28 |
| `JAVASCRIPT-NEXTJS-T` (142207722) | POST /_not-found/page | 7 | 2026-08-22, той самий інцидент, `firstSeen` збігається з S до мілісекунди |
| `JAVASCRIPT-NEXTJS-C` (140258262) | /char/:id | 14 | 2026-08-12 → 2026-08-16 |

**Доказ.** `firstSeen` S і T — `2026-08-22T07:36:41.443` і `.384` — 60 мс різниці, той самий
маршрут-збій одного деплойного вікна: клієнт із JS-бандлом попередньої збірки шле POST на
Server Action, ID якого сервер після деплою вже не знає («Failed to find Server Action» /
`UnrecognizedActionError`), Next падає в `/_not-found` і намагається розпарсити POST-тіло як
FormData — звідси T.

**Живий?:** так, і не «одна поломка» — S триває **6 днів після останнього деплою в git-історії**
(2026-08-23 18:27, `0bcbcba`), тобто це не залишок одного інциденту, а системна поведінка, що
повторюється щоразу, коли вкладка лишається відкритою через новий деплой. Причина — сам механізм
Next.js Server Actions при синьо-зеленому переключенні ([deploy.yml](../../.github/workflows/deploy.yml)),
не конкретний рядок коду. **Де:** не локалізовано (архітектурне, не файл:рядок).

**Скільки людей:** userCount=0 (D-002). Сирі події: 9+7+14 = 30 за родину.

**Статус:** відкрито. Тріаж не лагодить (правило цілі) — типове мʼяке лагодження такого класу
помилок (детекція неспівпадіння версії й `location.reload()`) лишається окремим рішенням
власника, не цієї сесії.

## Що лишається за межами цієї сесії

Кроки 5-7 [KR21.1](kr21.1-sentry-triage.md) (шумофільтри в `sentry-options.ts`, `Resolve`/`Ignore`
