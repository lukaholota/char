# O21 — питання до власника

Формат: питання → варіанти → рекомендація. Агент, який упирається в питання, **дописує рядок
сюди й іде далі по решті роботи**; він не зупиняє KR і не вирішує сам.

## Відкриті

### 3. Що робити з підтвердженими дефектами всередині цієї цілі

Ціль за задумом лише тріажить: знаходить, доводить, записує. Виправлення — окрема робота з
тестом навколо ([CLAUDE.md](../../CLAUDE.md), «спершу зафіксуй поведінку»).

**Варіанти:**
- **А.** Тріаж завершується реєстром; лагодження — окремим KR після перегляду списку.
- **Б.** Агент одразу лагодить те, що виявиться дешевим і безпечним.

**Рекомендація:** А. Порядок лагодження задає «скількох людей зачіпає», а це видно тільки коли
зібрано весь список. Виняток, який варто дозволити наперед: однорядкові поломки, що ламають
створення персонажа, — їх безглуздо тримати в черзі.

## Закриті

### ~~4. Як лагодити [D-001](defects.md)~~ — **закрито 2026-08-28: варіант А**

`Feature.engName` унікальний на всю базу ([schema.prisma:405](../../prisma/schema.prisma)), а в
D&D англійські назви рис повторюються: 14 різних рис у сідах ділять назву. Наслідок — риса
показує чужий текст (див. [D-001](defects.md)). Виправляти текст безглуздо: наступний прогін
сіда поверне все назад, що вже одного разу й сталося.

**Варіанти:**
- **А. Розвести назви, унікальність лишити.** `Psychic Blades` → `Psychic Blades (College of
  Whispers)` і `Psychic Blades (Soulknife)`, і так для 14 випадків: правка сідів, SQL для
  робочої бази (розділити злитий рядок і перевісити зв'язки), плюс тест, який падає, якщо два
  об'єкти рис у сідах узяли однаковий `engName`.
- **Б. Зняти `@unique` і зробити ключ складеним.** Чесніше моделює предметну область, але
  `engName` — це ключ, на якому свідомо стоїть рушій правил
  ([hit-points.ts:6](../../src/rules/hit-points.ts), `hasFeatureByEngName` у
  [bonus-calculator.ts:199](../../src/lib/logic/bonus-calculator.ts)). Тобто це вже не правка
  даних, а зміна інваріанта, на якому стоїть математика персонажа.

**Рекомендація:** А. Лагодить те, що бачить користувач, не чіпаючи інваріанта рушія, і дає
тест, який утримає виправлення — саме його бракувало минулого разу. Б варта окремої розмови,
але не під приводом одного баг-репорта з редіту.

**Рішення власника 2026-08-28: А.** Зроблено того ж дня — сіди, тест і SQL. Перша спроба на
робочій базі свідомо відкотилася на гейті (риси, що видаються вибором раси, лишали
`pers_feature` без перевішування — на контентному клоні цього не видно, бо там немає
персонажів); полагоджено кроком 2b і перевірено на `spells_scratch`, повній копії з 9 186
персонажами. **Лишилось власнику:** ще раз застосувати
[db/changes/2026-08-28-split-colliding-feature-eng-names.sql](../../db/changes/2026-08-28-split-colliding-feature-eng-names.sql)
до робочої бази і зробити `bun run db:pull`.

### ~~1. Доступ до Sentry~~ — **закрито 2026-08-28**

Токена Sentry API в проєкті немає: у CI лежить лише `NEXT_PUBLIC_SENTRY_DSN`, у `.env*` —
нічого. Без доступу KR21.1 не має входу.

**Варіанти:**
- **А.** Власник створює в `de.sentry.io` user auth token з правами `org:read`, `project:read`,
  `event:read` (без `project:write`) і кладе його в `.env.local` як `SENTRY_READ_TOKEN`.
- **Б.** Власник сам вивантажує список issue й кладе JSON у `inbox/sentry-issues.json`.

**Як закрито:** власник поклав у `.env` User Auth Token (`SENTRY_TOKEN`, `sntryu_…`) з
адмінськими правами. Знімок знято скриптом — 29 issue. Зауваження на майбутнє: токен ширший,
ніж треба тріажу; якщо колись переробляти — досить `org:read`, `project:read`, `event:read`.

**Варіанти:**

і розібраний як [R-001](reddit-claims.md). Анонімний доступ до Reddit API при цьому закритий
(403 на всі варіанти `curl`, WebFetch теж), тож дослівний текст дав власник.
