# EXPLAIN відкриття персонажа — 2026-09-26

На пряме прохання власника виконано на **робочій `spells`, PostgreSQL 17.11**.
Початкові плани — справжні `public`-таблиці. Порівняння індексів — тимчасові копії тих
самих даних на тому самому сервері, в одному зʼєднанні. Дані записів не експортувалися.
Під час аналізу постійні індекси й таблиці не змінено; усі тимчасові таблиці видалено
й це перевірено. Після аналізу власник застосував два запропоновані індекси; нижче є
повторні виміри вже на індексованих production-таблицях.

## Результат

Мілісекунди виконання на сервері, p50 із 15 запусків після двох прогрівальних запусків.
Типовий персонаж обраний за медіанною кількістю рядків на персонажа в кожній таблиці.

| Таблиця | Рядків | Рядків типового персонажа | Робоча база | TEMP без індексу | TEMP з індексом |
|---|---:|---:|---:|---:|---:|
| `pers_weapon` | 38 680 | 3 | 1,764 | 1,713 | 0,029 |
| `pers_armor` | 11 080 | 1 | 0,586 | 0,564 | 0,021 |
| `pers_magic_item` | 1 196 | 2 | 0,071 | 0,064 | 0,020 |
| `pers_infusion` | 388 | 4 | 0,033 | 0,037 | 0,016 |

До застосування індексів у production всі чотири запити — `Seq Scan`. Для зброї відсіюється 38 677 рядків і
читається 268 сторінок із shared buffers; для броні — 11 079 рядків і 115 сторінок.
Після індексу тимчасової таблиці — `Index Scan`, 2–3 сторінки для типового персонажа.
Перевірені також найбільший набір і порожній результат: перехід до індексу повторюється
в усіх чотирьох таблицях. Найбільші набори: зброя 14, броня 4, предмети 13, вливання 4.

На цьому короткому прогоні p95 типового production-запиту зброї — 6,122 мс, броні —
0,731 мс. З 15 вимірів оцінка p95 груба; це не довготривалий профіль затримок.

**Рекомендація:** додати `pers_weapon(pers_id)` і `pers_armor(pers_id)`.
Вони прибирають непотрібне сканування десятків тисяч рядків і покращують масштабування.
Для предметів і вливань нинішній абсолютний виграш — лише 0,02–0,05 мс; індекси там
залишаються нижчим пріоритетом, без SQL у цій пропозиції.

**Застосовано власником 26.09; перевірено о 07:58 UTC.** Обидва production-запити
тепер використовують `Index Scan` і читають по 3 сторінки з shared buffers.

| Таблиця | До, p50 мс | Після, p50 мс | Після, p95 мс | Індекс |
|---|---:|---:|---:|---|
| `pers_weapon` | 1,764 | 0,020 | 0,025 | `pers_weapon_pers_id_idx` |
| `pers_armor` | 0,586 | 0,018 | 0,021 | `pers_armor_pers_id_idx` |

Повторно виконано по 15 вимірів; це вже production-таблиці, не TEMP-копії.
Обидва індекси також відображені в поточних `prisma/schema.prisma` і `db/schema.sql`.
Повторний `db:pull` у цій сесії не запускався.

Сума чотирьох типових production-вимірів — **2,454 мс виконання SQL**. У порівнянні
на TEMP-копіях — 2,378 → 0,086 мс. Це не замір часу відкриття сторінки: запити можуть
виконуватися паралельно, TEMP-копії мають іншу фізичну упаковку, мережа й відкриття
зʼєднання не входять у `Execution Time`. Ці індекси самі по собі **не пояснюють секундну
затримку до взаємодії**. Вони не змінюють кількість SQL-запитів чи підключень.

## Методика й артефакти

Основний запит перевірки відповідає читанню всіх полів повʼязаної таблиці для одного
персонажа; вкладений граф персонажа цілком цією перевіркою не вимірювався:

```sql
EXPLAIN (ANALYZE, BUFFERS, SETTINGS, FORMAT JSON)
SELECT * FROM public.pers_weapon WHERE pers_id IN ($1) OFFSET $2;
```

Параметри — id вибраного персонажа й `0`. Для інших таблиць міняється лише назва.
Не вимикали `enable_seqscan`, не примушували планувальник використовувати індекс.
`statement_timeout = '5s'`, `lock_timeout = '500ms'`; жодна копійована таблиця не перевищила
3 МБ. Статистику оновлювали лише в тимчасових копіях:

```sql
CREATE TEMP TABLE char_index_audit_pers_weapon ON COMMIT DROP
AS TABLE public.pers_weapon;
ANALYZE char_index_audit_pers_weapon;
-- Вимір без індексу.
CREATE INDEX ON char_index_audit_pers_weapon (pers_id);
ANALYZE char_index_audit_pers_weapon;
-- Вимір з індексом, потім DROP TABLE і закриття зʼєднання.
```

У production-вимірах сторінки вже були в shared buffers: дискове читання тут не
оцінювалося. У TEMP-планах використовуються local buffers. Між читаннями production
продовжував приймати роботу користувачів, тому початкові counts і counts основного
прогону можуть відрізнятися на кілька рядків.

- [explain.json](explain.json) — розміри, параметри, індекси, представницькі повні плани
  й усі 15 значень часу для кожного сценарію та етапу.
- [catalog-and-cleanup.json](catalog-and-cleanup.json) — каталог ефектів, індекси після
  перевірки, підтвердження відсутності тимчасових таблиць.
- [after-owner-apply.json](after-owner-apply.json) — справжні production-плани й усі
  15 вимірів після застосування індексів власником.
- [SQL для власника](../../../db/changes/2026-09-26-pers-equipment-indexes.sql) — два
  індекси `CONCURRENTLY`; **застосовано власником**, схема вже відображає їх.
