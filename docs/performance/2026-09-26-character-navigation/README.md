# Production: затримки відкриття чарника — 2026-09-26

Read-only перевірка Sentry після EXPLAIN, за запитом власника знайти джерело секундної
затримки. Код застосунку, production і налаштування Sentry не змінювалися. Збережено
технічні spans, а не записи персонажів чи атрибути користувачів. Окремий браузерний
CPU-профіль у цій перевірці не знімався.

**Висновок:** є прямий доказ значної роботи головного потоку браузера під час відкриття.
У повільному прикладі серверні GET виконуються за 207–238 мс, натомість вісім довгих
кадрів тривають сумарно 1 334,9 мс. Атрибуція найчастіше починається з планувальника
React. Назва конкретного важкого компонента й частка офлайн-коду ще не визначені.
Окремий приклад показує багатосекундне завантаження клієнтського JS.

чанк прочитано: позиція `205281` вказує на функцію `O`, яка виконує callbacks черги

кадр із Cloudflare не означає 289 мс CPU Cloudflare; так само не можна всі 900,5 мс
віднести до React чи конкретної модалки. Потрібен CPU-профіль із перевіркою кандидатів
зі [списку оптимізацій](../../CHARACTER-OPENING-PERFORMANCE.md).

## Повторне відкриття й вибірка за добу

Через 40 секунд інше відкриття того самого листа, trace
`2f40d2eb8fbf4a9da50725445bc38f52`: navigation 1 202,5 мс, два GET 311,3 / 346,6 мс,
один довгий кадр 122 мс. Це показує змінність навантаження; не вважати перший приклад
типовим для всіх персонажів або постійною витратою офлайну.

Запит за останні 24 години на момент перевірки повернув **77 збережених довгих кадрів
у 33 traces**; у **46** перший скрипт — `MessagePort.onmessage` у тому самому чанку
планувальника React. Пагінація підтверджує, що наступної сторінки немає. Фільтр:
`span.op:ui.long-animation-frame transaction:"/char/:id"`.
Це вибірка Sentry, яка включає подальші взаємодії на листі, не 77 окремих відкриттів
і не кількість усіх подій у production.

Агрегований запит Sentry повертає більші counts/sums із поправкою на sampling.
Тому фактичні 77/46 пораховано за рядками raw spans. Confidence агрегованих p95
низький; їх не використовуємо для оцінки типового часу відкриття.

## Чому navigation ≈ 1000 мс ще не доказ

Trace `de50646c23384ae9a3ec941ae5e8cc9d`, 26.09 о 07:34:34 UTC: navigation триває
1 009,7 мс, але дочірніх запитів чи довгих кадрів у його інтервалі не видно.
Пізніші POST цього trace не є частиною цього інтервалу.

У встановленому Sentry `startIdleSpan` стандартний `idleTimeout` — 1000 мс.
Кінець обрізається до останнього дочірнього span лише за наявності descendants.
Тому близький до секунди navigation сам по собі може відображати таймер інструмента.
Не називати його TTI; у цих spans немає позначки готовності кнопок чарника.
