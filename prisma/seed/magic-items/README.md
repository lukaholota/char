# Корпус магічних предметів (O14)

У цій теці лежить увесь текст предметів, який їде в базу. Тексту в TS немає й бути не має.

| Файл | Що це | Скільки |
|---|---|---:|
| `baseline.json` | базовий корпус — переклад, який стояв до O14 | 472 |
| `batch-01…10.json` | партія перекладу з **aidedd** (O14), накладається зверху за `engName` | 268 |
| `batch-11…18.json` | партія перекладу з **5etools** ([KR16.4](../../../docs/o16-5etools-canon/kr16.4-magic-items.md)) | 191 |

Разом сідер кладе в базу **621** предмет: 472 базових, з яких 310 переписані партіями,
плюс 149 нових (`isNewToCatalog`) — 3 з aidedd і 146 з 5etools.

Формат партії однаковий для обох конвеєрів, і сідер їх не розрізняє. Різниця лише в тому,
хто будує контракт: для aidedd це `scripts/build-magic-item-seed-batch.ts`, для 5etools —
`scripts/5etools/build-item-seed-batch.ts` (`bun run build:item-batch --batch=NN`), а план
партій лежить у `data/5etools/item-batches.json` і пінує кожному рядку книгу й `magicItemId`.

`baseline.json` витягнуто з `magicItemSeed.ts` у KR14.5 — доти сідер був 4552 рядками
захардкоджених обʼєктів, і той файл був єдиною довговічною копією тексту каталогу. Читає
його [`../magicItemBaseline.ts`](../magicItemBaseline.ts), який падає, якщо записів не 472,
якщо `engName` чи `magicItemId` повторюються або якщо тип чи рідкість поза енумом.
Редагувати `baseline.json` руками не треба: черга O14 переписує його записи партіями.

## Чому не `db/changes/`

Партія 01 спершу приїхала разовим SQL-скриптом. Причина, чому так більше не роблять,
коротка: `db/changes/` за [Р2](../../../docs/DECISIONS.md) — журнал змін **схеми**, не
replayable. Разовий SQL не має ідемпотентності (повторний прогін не доводить нічого),
не лишає сліду, звідки взявся текст, і множиться на кожну наступну партію — а їх
попереду ще ~15. Сід натомість переганяється скільки завгодно разів і дає той самий
результат.

Той SQL лежить надгробком у `db/changes/2026-08-22-o14-magic-items-batch-01.sql` і
падає з помилкою, якщо його спробувати застосувати.

## Як накладається партія

Сідер робить `upsert` за `engName` — і це визначає все інше:

- **Перезаписуються лише поля партії**: `name`, `shortDescription`, `description`,
  `itemType`, `rarity`, `requiresAttunement`.
- **Не чіпаються** `bonusToAC`, `bonusToSavingThrows`, `weaponProficiencies*`,
  `noArmorOrShieldForACBonus` і звʼязок `_MagicItemToSpell`. Їх у партії просто немає,
  тому Prisma лишає колонки як були. Перевірено прогоном: `Cloak of Protection` зберіг
  `bonus_to_saving_throws`, `Bracers of Archery` — `weapon_proficiencies_special`,
  48 рядків `_MagicItemToSpell` уціліли.
- **`magicItemId` не рухається.** Це публічна адреса `/magic-items/NNNN`, і на неї
  посилається `pers_magic_item`. Якщо партія назве інший id, ніж стоїть у каталозі,
  сідер падає — див. `failOnIdDrift`.

## Конвеєр однієї партії

```
1. вибрати слуги          scripts/aidedd/scan-batch.ts        (тільки через bun)
2. перекласти             → data/aidedd/translations/magic-items-2014/batch-NN.json
3. розібрати сторінки     → data/aidedd/magic-items-2014.json  (id, тип, рідкість, налаштування)
4. зібрати сід-партію     npx tsx scripts/build-magic-item-seed-batch.ts --batch NN
                          → prisma/seed/magic-items/batch-NN.json     ← комітиться
5. перевірити             bun run seed:magic-items:test
6. застосувати            bun run seed:magic-items:prod              ← ВЛАСНИК, не агент
7. оновити каталог        bun run generate:magic-items
```

Кроки 1–3 — робоча зона перекладу (`data/aidedd/**`). Крок 4 — межа: далі йде контракт,
з якого будується база. Ділити їх варто саме тут, бо робоча зона переписується щоразу,
а контракт має пережити рік.

Крок 4 не редагують руками. Якщо в партії щось не так — правлять переклад на кроці 2
й пересобирають.

## Формат `batch-NN.json`

```json
{
  "batch": "01",
  "source": "aidedd.org — magic items 2014",
  "items": [
    {
      "magicItemId": 1024,
      "engName": "Cast-Off Armor",
      "slug": "cast-off-armor",
      "name": "Обладунок швидкого зняття [Cast-Off Armor]",
      "itemType": "ARMOR",
      "rarity": "COMMON",
      "requiresAttunement": false,
      "shortDescription": "…",
      "description": "…",
      "isNewToCatalog": false
    }
  ]
}
```

`isNewToCatalog: true` означає, що предмета в каталозі не було й сідер його створить.
Такий запис збільшує число предметів — і ламає тест, який фіксує розмір каталогу.
Це навмисно: розмір каталогу росте тільки свідомо.

## Слуги, яким партія не потрібна

`COVERED_BY_EXISTING_ENTRIES` у [`../magicItemBatches.ts`](../magicItemBatches.ts) —
це сторінки aidedd, що зліплюють в одну те, що в каталозі живе окремими записами.
Конвертер їх пропускає й каже про це вголос, щоб їх не рахували за дірку в покритті.

Зараз там 14 слугів на 72 наші записи. Приклад: `ammunition-1-2-or-3` покрито записами
`Ammunition +1` (93), `Ammunition +2` (94), `Ammunition +3` (95) — у них різна рідкість,
і злитий запис показав би в каталозі четвертий дубль без вибору рівня.

Це не єдине джерело бандлів: маніфест має власне поле `coversExistingEngNames` — 90 імен
на 14 інших сторінок, які партія таки розписала на варіанти. Разом 107 наших записів на
20 сторінок. Звіт розбіжностей дивиться в обидва джерела, і саме тому раніше показував
`Weapon +1/+2/+3` як записи без сторінки.

## Порядок партій не має значення

Партії накладаються за іменем файла, але результат від порядку не залежить: сідер
падає, якщо той самий `engName` або `magicItemId` трапляється у двох партіях. Тобто
партії мусять не перетинатися, і це перевіряється, а не мається на увазі.

## Ратифіковані термінологічні корекції

Після злиття `baseline.json` із партіями `magicItemBatches.ts` накладає вузький шар
`MAGIC_ITEM_TERMINOLOGY_CORRECTIONS`. Він призначений лише для рішень власника, які мають
одночасно виправити вже готові партії та bundle-записи без ручного редагування baseline.

Повний seed викликає шар у strict-режимі й падає, якщо будь-яка названа ціль відсутня; часткові
unit-фікстури можуть вимкнути цю вимогу. Нові переклади сюди не додають: спочатку рішення
власника і search alias старої назви, потім окрема поіменна корекція.
